# requirements — 요구사항 정의서 작성

입력: 원천 자료(인터뷰 메모·회의록·현행 문서·현행 소스 경로)와 대상 업무 범위. 없으면 먼저 묻는다.

## 1. 원천 목록
- 읽을 자료를 표로 정리한다: 자료 / 경로 / 종류(인터뷰·문서·소스) / 날짜.
- Word·Excel 원본을 못 읽으면 md 사본을 찾고, 없으면 "원본 미확인" 으로 적는다.

## 2. 요구사항 추출
- 자료에서 "해야 한다 / 필요하다 / 불편하다" 에 해당하는 문장을 모아 한 건씩 쪼갠다. 한 요구사항에 기능 하나.
- 기획 repo 에 요구사항 양식이 있으면 그 형식을 따른다 (뼈대 기본: `<기획 repo>/20-features/requirements.md` 요구 목록 한 줄씩 + 영역별 기능 문서 `<기획 repo>/20-features/_template.md` 의 수용 기준 표, 옛 뼈대 `<기획 repo>/01-requirements/_template.md`). 없으면 아래 형식.

| 칸 | 내용 |
|---|---|
| ID | `REQ-001` — 기존 번호를 다시 쓰지 않는다 |
| 구분 | 기능 / 비기능(성능·보안·운영) / 데이터 / 인터페이스 |
| 설명 | 누가, 무엇을, 왜 |
| 수용 기준 | 판정할 수 있는 조건 (수치·입력·결과) |
| 출처 | 원천 목록의 자료 이름 (경로 · 쪽 · `파일:라인` 은 표 아래 `> 출처:` 인용구로) |
| 우선순위 | 필수 / 권장 / 선택 |
| 상태 | 초안 / 검토중 / 확정 |

## 3. 검토
- 중복·충돌 요구사항을 찾아 묶거나 "결정 필요" 로 넘긴다.
- 판정할 수 없는 표현(빠르게·편리하게·충분히)이 남았는지 확인한다.
- 현행 소스에서 나온 요구사항은 소스 `파일:라인` 을 표 아래 인용구(`> 출처: REQ-001 …`)에 단다. 표 칸 · 본문에는 넣지 않는다.

## 4. 결과
- 요구사항 목록 파일과 "결정 필요" 목록(질문 / 누가 정하나 / 영향)을 기획 repo 에 쓴다. 뼈대 repo 면 결정 필요는 미결 목록(`<기획 repo>/90-decisions/open-questions.md`)에 `Q-` 행으로, 수용 기준은 기능 문서의 `AC-` 행으로 둔다.
- 요약: 건수(구분별) · 결정 필요 건수 · 원본 미확인 자료. 커밋은 사용자가 요청할 때만.
