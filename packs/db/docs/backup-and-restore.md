# 백업 · 복구 · 덤프

`packs/db/rules/30-data-change.md` §6 의 상세. 백업 정책 자체는 인프라 담당의 영역이고, 에이전트는 **작업 전에 확인하고 없으면 알리는** 역할이다.

## 1. 복구가 목표다

- 원하는 것은 백업이 아니라 **복구**다. 복구해 본 적 없는 백업은 믿지 않는다.
- 확인할 것: 백업이 실제로 존재하는가, 최근 것인가, **어디에 어떻게 풀어 봤는가(마지막 복구 시험 날짜·걸린 시간·확인한 건수)**.
- 흔한 착각: 백업이 있다고 가정 / 복구가 된다고 가정 / 복구 시간이 목표 안이라고 가정 / 복구하고 데이터를 조회해 보지 않음.

## 2. 용어

| 용어 | 뜻 |
|---|---|
| RPO | 잃어도 되는 최대 데이터 기간 (예: 5분 전까지는 되살려야 한다) |
| RTO | 복구에 걸려도 되는 최대 시간 |
| 논리 백업(덤프) | SQL·데이터 파일로 내보내기. 작은 범위·이관에 좋고 큰 DB 는 느리다 |
| 물리 백업 | 데이터 파일 단위. 큰 DB 에 빠르다 |
| 시점 복구(PITR) | 기본 백업 + 변경 로그 보관으로 **임의 시점**까지 되감기. "잘못된 UPDATE 직전" 으로 되돌릴 때 필요 |

- 여러 겹으로 지킨다: 되살리기 기간이 있는 삭제(휴지통), 주기 백업, 시점 복구, 원격 사본. 조용히 오래 번진 데이터 오염은 **오래된 시점**이 있어야 되살린다.
- 복제본(레플리카)은 백업이 아니다 — 잘못된 DELETE 도 그대로 복제된다.

## 3. 파괴적 작업 전 체크

| 범위 | 되돌릴 방법 |
|---|---|
| 수십~수천 행 | 대상 행을 백업 테이블(`<테이블>_bak_<날짜>`)이나 파일로 떠 두고, 되돌리는 SQL 을 미리 써 둔다 |
| 테이블 전체·DDL 삭제 | 그 테이블 덤프 + 최근 전체 백업 존재 확인 |
| 운영 전체에 영향 | 시점 복구 가능 범위가 작업 시각을 덮는지 확인, 작업 시각을 기록 (되감을 기준점) |

- 백업 테이블은 **보관 기한을 정해 지운다.** 개인정보가 든 사본이 운영 DB 에 무기한 남지 않게.
- 작업 시각을 초 단위로 기록해 둔다. 시점 복구 때 "몇 시 몇 분 직전" 을 정해야 한다.

## 4. 복구 절차의 원칙

- **새 위치(별도 인스턴스·스키마)에 먼저 푼다.** 운영 DB 위에 바로 덮어쓰지 않는다.
- 푼 뒤 건수·최근 행·핵심 합계로 **확인**하고, 필요한 행만 옮긴다.
- 복구 절차는 문서(런북)로 남기고, 시험할 때마다 걸린 시간과 결과를 기록한다.

## 5. 덤프 파일 다루기

- 덤프에는 개인정보·비밀번호 해시·토큰이 들어 있다. repo·공유 채널·이슈·에이전트 대화에 올리지 않는다.
- 로컬에 둘 때는 작업 폴더 밖·ignore 대상에 두고, 끝나면 지운다.
- 운영 덤프를 개발에 풀기 전에 가리기(`packs/db/rules/40-access-and-data.md` §3).
- 덤프·복구 명령의 대상 호스트·DB 를 실행 직전에 한 번 더 확인한다 — 복구 명령은 대상 DB 를 덮어쓴다.
