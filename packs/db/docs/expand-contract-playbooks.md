# 확장 → 전환 → 축소 작업별 순서

`packs/db/rules/20-schema-change.md` §4 의 상세. 작업마다 **배포 단위**로 나눈 순서다.
"릴리스 N" 은 한 번의 배포(모든 환경에 퍼지는 단위)를 뜻한다. 다운타임이 허용되는 환경이면 한 번에 해도 되지만 그 판단은 사용자에게 묻는다.

공통 전제

- 각 단계는 **바로 앞 단계의 코드와 호환**이어야 한다. 그래야 단계마다 따로 배포하고 따로 되돌릴 수 있다.
- DBMS 별 온라인 방식(동시 인덱스 생성, 검증 지연 제약, `ALGORITHM`/`ONLINE` 절 등)은 `packs/db/docs/dbms-notes.md` 와 stack 팩.
- 대량 백필은 스키마 마이그레이션과 분리해 묶음으로 돈다 (`packs/db/rules/30-data-change.md` §2).
- 끝나면 남은 단계가 없는지 확인한다. 반쯤 끝난 확장(양쪽 쓰기가 남은 상태)은 부채다.

## 1. 컬럼 추가

| 릴리스 | 할 일 |
|---|---|
| N | 컬럼 추가 — nullable 이거나 **상수** 기본값. 계산식·함수 기본값은 DBMS 에 따라 테이블 재작성 → 기본값 없이 추가 후 기본값 설정 → 백필 |
| N | 코드가 새 컬럼을 쓰기 시작 (추가와 같은 릴리스여도 된다 — 스키마가 먼저 적용되면) |
| N+1 (필요 시) | NOT NULL 로 조이기 → §5 |

## 2. 컬럼 삭제

| 릴리스 | 할 일 |
|---|---|
| N | 코드에서 읽기·쓰기 제거. ORM 에 "무시할 컬럼" 기능이 있으면 등록. 구 코드가 쓰는 NOT NULL 이면 먼저 nullable 로 |
| N+1 | 모든 환경에 N 이 배포된 것을 확인한 뒤 컬럼 삭제 (그 컬럼의 인덱스가 있으면 함께, 온라인 방식으로) |
| N+2 | 무시 목록 정리 |

- ORM 이 컬럼 목록을 캐시하는 방식이면 N 과 N+1 을 합치면 안 된다 — 구 프로세스가 사라진 컬럼을 INSERT 에 넣는다.
- Oracle 은 `SET UNUSED` 로 즉시 숨기고 나중에 물리 삭제할 수 있다.

## 3. 컬럼 이름 바꾸기

직접 `RENAME` 은 배포 중인 구 코드를 깨뜨린다. 이름 바꾸기 = 새 컬럼 추가 + 옛 컬럼 삭제.

| 릴리스 | 할 일 |
|---|---|
| N | 새 컬럼 추가. 코드가 **양쪽에 쓰고** 옛 컬럼에서 읽는다 (또는 DB 트리거로 동기화) |
| N (배포 후) | 새 컬럼 백필 → 검증 쿼리 0 |
| N+1 | 읽기를 새 컬럼으로. 쓰기는 여전히 양쪽 |
| N+2 | 옛 컬럼 쓰기 중단, 무시 목록 등록 |
| N+3 | 옛 컬럼 삭제 |

- 작은 테이블·짧은 점검 허용 시에는 단계를 줄일 수 있다. 줄일지 사용자에게 묻는다.
- 뷰·트리거·리포트 쿼리·다른 서비스가 옛 이름을 읽는지 전수 검색한다.

## 4. 컬럼 타입 바꾸기

| 릴리스 | 할 일 |
|---|---|
| N | 새 타입으로 새 컬럼 추가, 양쪽 쓰기 |
| N | 변환 백필 (변환 실패 행을 먼저 세어 본다 — 문자 → 숫자, 길이 초과, 시간대) |
| N+1 | 읽기 전환 |
| N+2 | 옛 컬럼 쓰기 중단 → 다음 릴리스에 삭제 |

- 재작성 없이 되는 타입 변경도 있다(길이 늘리기 일부 등). DBMS·버전마다 다르니 `packs/db/docs/dbms-notes.md` 로 확인하고, 확인 못 하면 위 순서를 쓴다.
- 정수 기본키를 64비트로 바꾸는 일은 참조하는 모든 외래키 컬럼까지 바꿔야 해 가장 비싸다 — 처음부터 64비트로.

## 5. NOT NULL 추가 (값이 이미 있는 컬럼)

| 릴리스 | 할 일 |
|---|---|
| N | 모든 쓰기 경로가 값을 채우게 코드 수정 (기본값 포함) |
| N (배포 후) | NULL 행 백필 → `count(*) WHERE col IS NULL` = 0 |
| N+1 | NOT NULL 제약 추가. 큰 테이블은 검증을 나눌 수 있는 DBMS 면 "검증 없이 추가 → 따로 검증" |

- NOT NULL **제거**는 먼저 해도 된다(구 코드는 여전히 값을 넣는다).

## 6. 기본값 바꾸기

| 릴리스 | 할 일 |
|---|---|
| N | 코드가 새 기본값을 **명시적으로** 넣게 수정 |
| N (배포 후) | DB 기본값 변경 |
| N+1 | 코드의 임시 처리 제거 |

- ORM 이 "기본값과 같으면 INSERT 에서 컬럼을 뺀다" 류로 동작하면, 캐시된 옛 기본값 때문에 순서가 틀리면 엉뚱한 값이 들어간다.

## 7. 외래키 추가

| 단계 | 할 일 |
|---|---|
| 1 | 자식 컬럼 인덱스 먼저 (온라인 방식) |
| 2 | 고아 행 세기 → 정리 (파괴적 변경이면 건별 승인) |
| 3 | 외래키 추가. DBMS 가 지원하면 "검증 없이 추가"(짧은 잠금) → 별도 트랜잭션에서 검증 |

- 외래키 추가·삭제는 **양쪽 테이블**을 잠근다. 트래픽 많은 테이블 여러 개에 한 번에 걸지 않는다(한 마이그레이션에 하나).
- 테이블을 지우기 전에 그 테이블을 가리키는 외래키부터 하나씩 따로 지운다.

## 8. 유일 제약 추가

| 단계 | 할 일 |
|---|---|
| 1 | 중복 세기 → 정리 방법 결정 (어느 행을 남길지 사용자에게) |
| 2 | 앱이 새 중복을 만들지 않게 수정 |
| 3 | 유일 인덱스를 온라인 방식으로 → 필요하면 그 인덱스로 제약 연결 |

- NULL 처리(여러 NULL 허용 여부)와 소프트 삭제된 행 제외 여부를 정한다.
- 문서 DB 는 인덱스 생성이 끝날 때 위반을 발견하고 전체를 실패시킨다 — 먼저 센다.

## 9. enum · 코드값

| 작업 | 순서 |
|---|---|
| 값 추가 | 스키마에 값 추가 → 코드가 새 값을 쓰기 시작. 구 코드가 모르는 값을 읽어도 죽지 않는지 본다 |
| 값 이름 변경 | 새 값 추가 → 코드가 둘 다 읽기 → 새 값 쓰기 → 백필 → 옛 값 제거(가능한 DBMS 만) |
| 값 제거 | 코드에서 쓰기 중단 → 데이터 정리 → 타입·제약 교체 (PostgreSQL enum 은 값 삭제 불가 → 새 타입으로 교체) |

## 10. 테이블 이름 바꾸기 · 삭제 · 나누기

- **이름 바꾸기**: 새 테이블 만들기 → 양쪽 쓰기 → 백필 → 읽기 전환 → 옛 테이블 쓰기 중단 → 삭제. 호환 뷰(옛 이름 → 새 테이블)로 이어 주는 방법도 있다(DBMS·ORM 이 허용하면).
- **삭제**: 릴리스 N 에서 코드 참조 제거 → N+1 에서 가리키는 외래키 하나씩 제거 → 테이블 삭제. 삭제 전 백업·건수 기록·승인.
- **나누기·합치기**: 이름 바꾸기와 같은 순서를 컬럼 묶음 단위로.

## 11. 문서 DB · JSON 필드

- 필드 추가: 선택 필드로 추가 → 코드가 쓰기 → (필요하면) 검증 규칙에 필수로. 기존 문서가 규칙에 안 맞아도 새 쓰기만 검사하는 모드가 있으면 그것으로 시작.
- 필드 이름·구조 변경: 문서에 스키마 버전 필드를 두고, 코드가 **옛·새 구조를 모두 읽게** 한 뒤 점진적으로 옮긴다. 두 구조가 공존하는 동안 쿼리·인덱스가 양쪽을 덮는지 본다.
- "알 수 없는 속성 금지" 류 검증은 구 코드가 새 속성을 만나면 깨진다 — 추가는 검증부터 느슨하게.
