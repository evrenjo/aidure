# 위험한 스키마 작업 목록 — DBMS 공통

`packs/db/rules/20-schema-change.md` 가 가리키는 참고 표다. 마이그레이션 린터(strong_migrations·Squawk 등)가
잡는 항목과 무중단 마이그레이션 지침(GitLab 등)을 DBMS 와 무관한 말로 모았다.
**DBMS 별 문법은 `packs/db/docs/dbms-notes.md` 와 stack 팩**, 작업별 단계 순서는 `packs/db/docs/expand-contract-playbooks.md`.
프로젝트에 린터가 있으면 그 결과가 우선이다. 린터가 원시 SQL 을 못 보는 경우가 많으니 원시 SQL 은 이 표로 직접 검토한다.

## 1. 구 코드를 깨뜨리는 변경 (배포 순서 문제)

| 작업 | 왜 위험한가 | 안전한 순서 |
|---|---|---|
| 컬럼 삭제 | 구 코드가 아직 읽거나, ORM 이 컬럼 목록을 캐시해 INSERT 에 넣는다 | 코드에서 제거(무시 목록) → 배포 → 다음 릴리스에 삭제 |
| 컬럼·테이블·스키마 이름 바꾸기 | 배포 중 구 코드가 옛 이름을 찾는다 | 새 이름 추가 → 양쪽 쓰기 → 백필 → 읽기 전환 → 옛 것 삭제 |
| 컬럼 타입 바꾸기 | 구 코드 호환 깨짐 + 대개 재작성·긴 잠금 | 새 컬럼 → 양쪽 쓰기 → 백필 → 전환 → 옛 컬럼 삭제 |
| NOT NULL 추가 | 값을 안 넣는 구 코드의 INSERT 실패 + 전체 검사 | 모든 쓰기가 값 채움 → 백필 → (지원하면) 검증 나눠서 → NOT NULL |
| 기본값 변경 | ORM 이 캐시한 옛 기본값으로 INSERT | 코드가 새 값을 명시적으로 → DB 기본값 변경 → 정리 |
| enum 값 이름 변경·삭제 | 구 코드가 새 값을 모르거나 옛 값을 쓴다 | 새 값 추가 → 둘 다 읽기 → 새 값 쓰기 → 백필 → 옛 값 제거 |
| 엄격한 JSON 스키마에 속성 추가 | "모르는 속성 금지" 검증에 구 코드가 걸린다 | 선택 속성으로 먼저 → 다 배포된 뒤 필수화 |
| 테이블 삭제 | 되돌릴 수 없음, 가리키는 외래키가 참조 테이블을 잠근다 | 코드 참조 제거 → 외래키 하나씩 제거 → 백업·승인 → 삭제 |

## 2. 긴 잠금 · 테이블 재작성

| 작업 | 왜 위험한가 | 안전한 방법 |
|---|---|---|
| 인덱스 생성 (일반) | 생성 동안 쓰기 차단 | DBMS 의 온라인 방식. 실패하면 남은 반쪽 인덱스 정리. 새로 만든 빈 테이블이면 일반 방식도 괜찮다 |
| 인덱스 삭제 (일반) | 짧지만 강한 잠금 + 그 인덱스를 쓰던 쿼리가 느려짐 | 사용 여부(통계) 확인 → 온라인 방식 |
| 외래키 추가 | 기존 행 검증 동안 **양쪽 테이블** 쓰기 차단 | 자식 컬럼 인덱스 먼저 → (지원하면) 검증 없이 추가 → 따로 검증 |
| CHECK 제약 추가 | 전체 검사 동안 잠금 | (지원하면) 검증 없이 추가 → 따로 검증 |
| 유일 제약 추가 | 유일 인덱스 생성과 같다 + 중복 있으면 실패 | 중복 정리 → 유일 인덱스를 온라인으로 → 그 인덱스로 제약 |
| 계산식·함수 기본값 컬럼 추가 | DBMS 에 따라 테이블 재작성 | 기본값 없이 추가 → 기본값 설정 → 백필 |
| 자동 증가·저장형 생성 컬럼 추가 | 테이블 재작성 | 새 테이블로 옮기기, 또는 트리거·가상 컬럼 |
| 기본키 추가·변경 | 테이블 재구성 | 처음 만들 때 정한다. 바꿔야 하면 새 컬럼·인덱스 준비 후 교체 |
| 정수 키를 64비트로 | 키와 모든 참조 컬럼 재작성 | 새 컬럼 + 동기화 + 백필 + 인덱스·외래키 재생성 + 교체 (여러 릴리스) — 처음부터 64비트로 |
| 테이블 재구성·압축·통계 전체 갱신류 | 전체 잠금 | 온라인 도구·온라인 재정의, 한가한 시간 |
| 한 마이그레이션에 여러 큰 DDL | 잠금이 겹쳐 대기열 폭증 | 트랜잭션 하나에 큰 잠금 하나, 외래키는 마이그레이션 하나에 하나 |
| 잠금 대기 제한 없는 DDL | 앞 트랜잭션을 기다리는 동안 그 테이블 전체가 멈춤 | 짧은 잠금 대기 제한 + 재시도 |
| 트랜잭션 안에서 온라인 인덱스 | DBMS 에 따라 오류 | 도구의 "트랜잭션 끄기" 옵션으로 그 마이그레이션만 분리 |

## 3. 데이터를 잃거나 망가뜨리는 변경

| 작업 | 왜 위험한가 | 안전한 방법 |
|---|---|---|
| `DROP`·`TRUNCATE` (CASCADE 포함) | 되돌릴 수 없음, 연쇄 범위가 넓음 | 사용처 0 확인 → 백업 → 건별 승인 |
| 테이블 만들기의 "있으면 지우고 만들기" 옵션 | 기존 테이블을 조용히 지운다 | 쓰지 않는다 |
| 생성기가 만든 "삭제 + 추가" (실제로는 이름 바꾸기) | 데이터가 사라진다 | 파일을 읽고 이름 바꾸기로 고치거나 확장 → 축소로 |
| 스키마 마이그레이션 안의 대량 UPDATE/DELETE | 배포 지연, 긴 트랜잭션, 실패 시 전부 되감기 | 별도 데이터 작업으로 묶음 처리 |
| 타입 좁히기·길이 줄이기 | 값이 잘리거나 변환 실패 | 넘치는 행을 먼저 센다 → 정리 → 변경 |
| 외래키 검사 끄고 적재 | 고아 행이 조용히 남는다 | 켠 뒤 정합 검사 쿼리(0 이어야 정상) |
| 원시 SQL 실행 | 린터가 안을 못 본다 | 이 문서로 직접 검토하고 이유를 주석에 |

## 4. 설계 단계에서 피할 것 (린터 권고)

| 항목 | 이유 |
|---|---|
| 32비트 자동 증가 키 | 다 차면 바꾸기가 매우 비싸다 |
| 시간대 없는 시점 타입 | 기준이 모호해진다 (`packs/db/rules/60-data-modeling.md`) |
| 근거 없는 짧은 문자열 길이 | 늘리는 비용이 DBMS 마다 다르다 |
| 고정 길이 문자 타입 | 공백 채움으로 비교가 헷갈린다 |
| 부동 소수 금액 | 반올림 오차 |
| 이름 없는 제약·인덱스 | 나중에 지우거나 비교할 수 없다 |
| 스키마를 적지 않은 DDL (여러 스키마 환경) | 엉뚱한 스키마에 만들어진다 |
| 재시도에 약한 DDL | 중간 실패 후 다시 돌리면 "이미 있음" 으로 깨진다 → `IF NOT EXISTS` |
