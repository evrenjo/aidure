## 스키마 변경 체크리스트

작업별 단계 순서는 `packs/db/docs/expand-contract-playbooks.md`, 위험한 작업 목록은 `packs/db/docs/dangerous-operations.md`,
DBMS 별 차이는 `packs/db/docs/dbms-notes.md` 에 있다. PostgreSQL 문법은 stack 팩이 정본이다.

### 1. 정본 찾기 — 마이그레이션 도구가 있으면 그것을 따른다

손대기 전에 그 repo 가 스키마를 무엇으로 관리하는지 확인한다.

| 흔적 | 도구 | 스키마 변경 = |
|---|---|---|
| `db/migration/V*__*.sql`, `flyway.conf`, `spring.flyway.*` | Flyway | 새 버전 파일(`V`) 추가. 뷰·프로시저처럼 매번 다시 만드는 것만 반복 파일(`R__`)로 |
| `changelog*.xml·yaml·json`, `spring.liquibase.*` | Liquibase | 새 changeSet 추가 (한 changeSet 에 변경 하나) |
| `alembic.ini`, `alembic/versions/` | Alembic | `alembic revision` 으로 새 리비전 |
| `prisma/schema.prisma`, `prisma/migrations/` | Prisma | 스키마 수정 후 개발용 명령으로 생성, 배포 환경은 적용 전용 명령만 <!-- refs:ignore --> |
| `*/migrations/0*.py` | Django | `makemigrations` 로 생성, `sqlmigrate` 로 SQL 확인 |
| `db/migrate/` | Rails | 생성기로 새 파일, 스키마 덤프 파일도 함께 커밋 |
| `Migrations/` + `*.Designer.cs` | EF Core | `migrations add` 로 생성, 배포는 스크립트·번들로 |
| knex·TypeORM·Sequelize·golang-migrate·Goose 폴더 | 각 도구 | 그 도구의 생성 명령으로 새 파일 |
| 위가 없고 앱이 기동 때 읽는 DDL 파일만 있음 | (도구 없음) | 그 DDL 파일이 정본 |

- 도구도 DDL 파일도 못 찾으면 추측으로 만들지 말고 사용자에게 정본 위치를 묻는다.
- 버전 번호·파일 이름 규칙은 기존 파일을 따른다. 브랜치 간 번호 충돌은 MR·PR 직전 통합 브랜치를 받은 뒤 확인한다.

### 2. 마이그레이션 파일 규칙

- **이미 적용된 마이그레이션은 고치지 않는다.** 체크섬 검증에 걸리거나, 이미 반영된 환경과 새 환경이 조용히 갈라진다. 고칠 게 있으면 **새 파일로 앞으로 고친다.**
  - 아직 아무 공유 환경에도 적용되지 않은(내 로컬에만 있는) 파일은 고쳐도 된다. 적용 여부가 불확실하면 적용된 것으로 본다.
  - 체크섬을 강제로 맞추는 명령(repair·resolve·changelog sync·검증 체크섬 지정 류)은 **사용자 승인 없이 쓰지 않는다.**
- **지우지도 않는다.** 필요 없어진 마이그레이션은 본문을 비우고(no-op) 이유를 주석으로 남긴다. 파일이 사라지면 이력 테이블과 어긋난다.
- **생성기가 만든 마이그레이션은 그대로 믿지 않는다.** 이름 바꾸기가 삭제+추가로 나와 데이터가 사라지고, 이름 없는 제약은 누락된다. 파일을 읽고 의도와 다르면 고친 뒤 커밋한다.
- **한 마이그레이션에는 한 가지 변경.** 잠금이 큰 DDL 여러 개, 스키마 변경과 대량 데이터 변경을 한 파일에 묶지 않는다. 데이터 쪽은 → `packs/db/rules/30-data-change.md`
- 제약·인덱스는 **이름을 붙여** 만든다(나중에 지우거나 비교할 수 있게). 이름 규칙은 기존 스키마를 따른다.
- **되돌리는 방법**(down·rollback)을 도구가 지원하면 함께 쓴다. 되돌릴 수 없는 변경(데이터 손실)이면 도구의 "되돌릴 수 없음" 표시를 쓰고 주석에 적는다.
- 트랜잭션에 묶이지 않는 DDL 을 쓰거나 DDL 이 암묵 커밋되는 DB 면, 중간 실패 후 다시 돌려도 되게 **`IF NOT EXISTS` / `IF EXISTS` 로** 짠다.
- 마이그레이션 안에서 **앱의 현재 모델·엔티티 클래스를 쓰지 않는다.** 모델이 바뀌면 옛 마이그레이션이 깨진다. 도구가 주는 과거 시점 모델이나 SQL 을 쓴다.

### 3. 정본에서 따라오는 것 — 순서대로 훑는다

해당 없는 항목은 "해당 없음" 이라고 적고 넘어간다(안 본 것과 구분).

| # | 대상 | 할 일 |
|---|---|---|
| 1 | **정본** (마이그레이션 또는 DDL) | 컬럼·기본값·NOT NULL·코멘트·인덱스·제약 반영. 항상 필수 |
| 2 | **생성 문서** (ERD·스키마 덤프·초기화 스크립트) | 생성기를 다시 돌린다. **손으로 고치지 않는다** |
| 3 | **시드·기준 데이터** | 영향 있으면 함께 수정 → `packs/db/rules/70-seed-and-test-data.md` |
| 4 | **데이터 이관 도구·스텝** | 그 테이블을 읽거나 쓰는 스텝이 있으면 정합 수정 |
| 5 | **ORM 매핑·쿼리** | 엔티티·조회·쓰기 경로를 전수 검색해 새 계약을 충족하는지 확인 |
| 6 | **DB 반영** | 개발 DB 의 **해당 스키마 전부**에. 공유·고객 DB 는 요청받았을 때만. 도구가 있으면 도구로 반영한다 |

### 4. 확장 → 전환 → 축소 (expand / migrate / contract)

배포 중에는 **구 버전과 새 버전 코드가 같은 스키마를 동시에 쓴다**(롤링·블루그린·카나리, 배포 뒤 되돌리기).
그래서 스키마는 늘 **바로 앞·뒤 버전 코드 모두와 호환**이어야 한다.

| 단계 | 스키마 | 코드 |
|---|---|---|
| 1 확장 | 새 컬럼·테이블 **추가만** (nullable 이거나 기본값) | 구 코드 그대로 동작 |
| 2 전환 | 필요하면 백필 | 새 구조에 쓰고(필요하면 양쪽에), 읽기를 새 구조로 옮긴다 |
| 3 축소 | 구 컬럼·테이블 **삭제** | 구 구조를 안 쓰는 코드가 **그 환경에 배포된 뒤** |

- **이름·타입 바꾸기도 삭제다.** 새 이름으로 추가 → 양쪽 쓰기 → 백필 → 읽기 전환 → 옛 것 쓰기 중단 → 다음 릴리스에 삭제.
- **컬럼 삭제는 코드에서 먼저 뺀다.** ORM 이 컬럼 목록을 캐시하거나(무시 목록 기능이 있으면 먼저 등록) 기동 때 스키마를 검증하면, 순서가 틀릴 때 **운영 중인 구 버전이 오류를 내거나 재기동 순간 내려간다.** 빌드는 DB 를 보지 않아 빌드에서 드러나지 않는다.
- NOT NULL 추가는 **모든 쓰기 경로가 값을 채우고 백필이 끝난 뒤.** 제거는 먼저 해도 된다.
- **기본값 변경도 두 단계다.** ORM 이 기본값을 캐시해 "기본값과 같으면 INSERT 에서 뺀다" 류로 동작하면 구 기본값이 조용히 들어간다.
- JSON 스키마·문서 DB 필드도 같다 — 새 필드는 선택 항목으로 먼저, 필수화는 다 배포된 뒤.
- 축소(삭제)는 **환경마다 새 빌드가 뜬 것을 확인한 뒤 그 환경에만** 돌린다. 전 환경을 한 번에 지우지 않는다.
- 확장만 하고 축소를 잊지 않는다. 양쪽 쓰기가 남으면 그 자체가 부채다 — 남은 단계를 인계 기록에 적는다.
- 다운타임이 허용되는 환경(점검 시간이 있는 사내 시스템 등)이면 한 번에 바꿔도 된다. 그 판단은 사용자에게 묻는다.

### 5. 잠금 · 큰 테이블

DDL 은 대개 테이블 잠금을 잡는다. 앞의 긴 트랜잭션을 기다리는 동안 **뒤의 모든 조회·쓰기도 줄 서서 멈춘다.**

- DDL 앞에 **짧은 잠금 대기 제한**(수 초)을 걸고, 실패하면 잠시 뒤 다시 시도한다. 문장 자체의 실행 제한은 넉넉히. 도구에 잠금 재시도 기능이 있으면 쓴다.
- 잠금이 큰 DDL 은 **한 트랜잭션에 하나씩.** 트래픽이 많은 테이블 여러 개를 한 마이그레이션에 묶지 않는다. 외래키 추가·삭제는 **양쪽 테이블**을 잠근다.
- 테이블을 다시 쓰거나 전체를 훑는 변경(타입 변경·일부 기본값 컬럼 추가·인덱스 생성·제약 검증·PK 변경)은 **DBMS 의 온라인 방식**을 쓴다. 온라인 옵션을 명시해 두면 불가능할 때 느린 방식으로 조용히 넘어가지 않고 실패한다.
- 인덱스는 **필요를 실행 계획으로 확인한 뒤** 만든다. 인덱스마다 쓰기가 느려진다. 운영 규모 테이블의 인덱스 생성은 오래 걸리니 배포와 분리할지 사용자에게 묻는다.
- 운영과 같은 규모의 데이터에서 걸리는 시간을 모르면 추측하지 말고 복제본에서 재거나 사용자에게 묻는다.
- 마이그레이션이 도는 동안 긴 트랜잭션·배치가 돌고 있으면 기다린다. 배치 시간표를 모르면 묻는다.

### 6. 시험 — 사본에서 올리고 내린다

- 새 마이그레이션은 **빈 DB 에 처음부터 끝까지** 적용되는지, 그리고 **현재 운영 스키마와 같은 사본** 위에 적용되는지 둘 다 본다.
- down·rollback 이 있으면 올림 → 내림 → 올림 을 한 번 돌린다.
- **DDL 이 트랜잭션에 묶이지 않는 DB(MySQL·MariaDB·Oracle 은 DDL 앞뒤로 암묵 커밋)** 는 롤백으로 시험할 수 없다. 로컬·복제본에서 먼저 돌린다.
- 운영 적용 전에 도구가 **실행될 SQL 을 뽑아 보여 주는 기능**(dry-run·script·sqlmigrate 류)이 있으면 그 SQL 을 검토한다.
- 적용 뒤 앱 테스트를 돌린다(테스트 실행 규칙은 프로젝트 규칙을 따른다).
- **운영 적용은 배포 파이프라인의 한 단계로** 한다. 앱 인스턴스마다 기동 때 마이그레이션을 돌리게 하지 않는다 — 여러 인스턴스가 동시에 돌고, 앱 계정에 DDL 권한이 필요해진다. 기존 방식이 그렇다면 바꾸자고 제안만 한다.
