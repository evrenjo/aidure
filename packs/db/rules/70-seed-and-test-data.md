## 시드 · 기준 데이터 · 테스트 데이터

### 1. 세 종류를 섞지 않는다

| 종류 | 예 | 어디에 | 운영에 들어가나 |
|---|---|---|---|
| **기준 데이터** | 코드값·국가·권한·메뉴 | 마이그레이션(버전 관리됨) 또는 프로젝트의 기준 데이터 파일 | 들어간다 |
| **개발용 시드** | 샘플 사용자·샘플 주문 | 시드 스크립트 | **안 들어간다** |
| **테스트 데이터** | 테스트마다 만드는 행 | 테스트 코드(팩토리·픽스처) | 안 들어간다 |

- 프로젝트가 어느 것을 어디에 두는지 먼저 찾는다. 새 데이터가 어느 종류인지 정하고 그 자리에 넣는다.
- 개발용 시드·테스트 계정이 운영 배포 경로에 섞이지 않게 한다(환경 조건으로 막혀 있는지 확인).

### 2. 기준 데이터 · 시드 규칙

- **멱등으로** 쓴다 — 있으면 건너뛰거나 갱신(`NOT EXISTS`·upsert·"찾거나 만들기"). 두 번 돌려도 같아야 한다. 단순 INSERT 는 두 번째 실행에서 깨지거나 중복을 만든다.
- 기준 데이터는 **고정 키**를 쓴다. 다른 테이블·코드가 그 키를 참조하기 때문이다. 키를 바꾸면 기존 행이 지워지고 새로 생기는 도구가 있다.
- 기준 데이터를 마이그레이션 밖에서 손으로 바꾸면 다음 적용 때 덮어쓰이거나 충돌한다. 바꾸려면 새 마이그레이션·시드 변경으로.
- **이미 적재된 DB 는 시드 파일을 고쳐도 자동으로 바뀌지 않을 수 있다**(처음 한 번만 도는 시드). 반영 방법(재적재·갱신 SQL)을 정하고 해당 스키마 전부에 적용한다.
- 시드가 참조하는 스키마가 바뀌면 시드도 같은 변경에서 고친다(`packs/db/rules/20-schema-change.md` §3).
- 순서가 있는 데이터(부모 → 자식, 외래키)는 파일 안 순서를 지킨다. 실패를 무시하고 계속 도는 적재 방식이면 **빠진 행이 조용히 남는다** — 적재 뒤 건수로 확인한다.
- 시드·기준 데이터에 실제 개인정보·운영 비밀번호를 넣지 않는다.

### 3. 테스트 데이터 · 테스트 DB

- 가능하면 **운영과 같은 DBMS·같은 주 버전**으로 테스트한다(컨테이너 등). 메모리 DB·다른 DBMS 로 대신하면 문법·잠금·정렬·시간대 차이를 못 잡는다. 프로젝트 방식이 다르면 따르되 그 한계를 알고 쓴다.
- 테스트 DB 스키마는 **마이그레이션으로 만든다**(수기 DDL·ORM 자동 생성이 아니라). 그래야 마이그레이션 자체가 매번 시험된다.
- 테스트마다 **필요한 데이터를 그 테스트가 만든다**(팩토리·빌더). 공유 픽스처에 기대면 테스트끼리 얽힌다.
- 테스트 사이 격리: 테스트마다 롤백하는 트랜잭션, 또는 테이블 비우기. 트랜잭션 롤백 방식은 **커밋 뒤에 도는 동작(커밋 훅·다른 커넥션에서 읽기)** 을 못 본다 — 그런 코드는 따로 시험한다.
- 운영 데이터 사본으로 테스트해야 하면 `packs/db/rules/40-access-and-data.md` §3 의 가리기를 먼저 한다.
- 시간·난수·순번에 기대는 테스트는 값을 고정하거나 주입한다. 테스트 결과가 실행 시각·순서에 따라 달라지지 않게 한다.
- 테스트 실행은 프로젝트 규칙(자동 실행 여부 등)을 따른다.
