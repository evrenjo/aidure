## 쿼리 코드 · DB 계정 · 개인정보

### 1. 쿼리 코드 — 값은 바인드, 식별자는 허용 목록

- 값은 **바인드 파라미터**(prepared statement·ORM·쿼리 빌더의 파라미터)로만 넣는다. 문자열 이어 붙이기·포맷팅으로 값을 넣지 않는다. 직접 이스케이프는 대책이 아니다(DBMS 마다 다르고 빠지는 경우가 있다).
- 테이블·컬럼 이름·정렬 방향·`LIMIT` 처럼 바인드가 안 되는 자리는 **코드에 적힌 허용 목록에서 골라** 넣는다. 사용자 입력을 그대로 쓰지 않는다.
- ORM 의 원시 SQL 창구, 저장 프로시저 안의 동적 SQL, `LIKE` 패턴·`IN` 목록도 같은 규칙이다(`IN` 은 파라미터를 개수만큼 만들거나 배열 파라미터로).
- 쿼리 로그·오류 메시지·예외에 **바인드 값(개인정보·비밀값)을 그대로 남기지 않는다.**
- 최소 권한은 **추가 방어**다. 파라미터화를 대신하지 않는다.

### 2. 계정 · 권한

| 계정 | 권한 |
|---|---|
| 앱 실행용 | 필요한 테이블의 조회·쓰기만. DDL·권한 부여 없음 |
| 마이그레이션용 | DDL. 배포 단계에서만 쓴다 |
| 사람(조회·운영) | 환경마다 따로, 운영은 조회 전용을 기본으로 |
| 관리자·소유자 | 앱·에이전트가 평소에 쓰지 않는다 |

- 환경마다 계정을 따로 둔다. 개발 계정으로 운영에 붙을 수 없어야 한다.
- 접속 정보는 코드·repo·문서·로그에 적지 않는다. 환경 변수·비밀 저장소·키체인 등 **출처만** 가리킨다. 실수로 커밋했으면 지우는 것으로 끝나지 않는다(이력에 남는다) — 비밀번호를 바꾸도록 사용자에게 알린다.
- 권한·계정을 만들거나 바꾸는 것(GRANT·REVOKE·CREATE USER·ROLE)은 파괴적 변경과 같이 **건마다 승인**받는다.
- 에이전트가 쓸 계정을 고를 수 있으면 **작업에 충분한 가장 약한 계정**을 쓴다. 조회만 할 거면 조회 계정.

### 3. 개인정보 · 데이터 복사 · 덤프

- 운영 데이터를 개발·시험 환경이나 로컬로 옮길 때는 **개인정보(이름·연락처·주소·식별번호·결제정보·건강정보·위치 등)를 가리거나 합성 데이터로 바꾼다.** 원본 그대로 옮겨야 하면 사용자 승인과 보관·삭제 계획이 먼저다.
- 가리기는 **복사본 자체를 바꾸는 것**(정적 마스킹·가명화·합성)이어야 한다. 조회 결과만 가리는 기능(동적 마스킹·뷰)은 권한 있는 사람과 추론 공격에 뚫리므로 복사의 대책이 아니다.
- 가린 뒤에도 **조인 관계·유일성·형식은 유지**되게 한다(같은 원본 → 같은 가명). 안 그러면 시험이 실제와 달라진다.
- 필요한 테이블·행·컬럼만 옮긴다(최소 수집·최소 보관).
- 덤프·추출 파일은 repo·공유 채널·이슈·에이전트 대화에 올리지 않는다. 작업이 끝나면 지운다.
- 답변·문서·검증표·테스트 픽스처에 실제 개인정보 값을 옮겨 적지 않는다. 건수·키·가린 값으로 쓴다.

### 4. 보존 기한 · 삭제 의무 · 로그

- 보존 기한·삭제 의무(탈퇴 회원·로그·법정 보관 기간)는 **프로젝트 규칙**을 따른다. 모르면 묻는다. 규칙이 있으면 그 삭제 작업이 **백업·복제본·소프트 삭제된 행·아카이브 테이블**까지 닿는지 본다.
- 새 개인정보 컬럼을 추가하면 **왜 필요한지, 언제 지우는지**를 설계 문서·주석에 남긴다. 필요 없으면 안 모은다.
- 앱 로그·감사 로그에는 접속 문자열·비밀번호·토큰·세션 값·결제정보를 남기지 않고, 이름·이메일·전화 같은 값은 가린다.
- 암호화·해시가 필요한 컬럼(비밀번호는 전용 해시 함수, 민감 정보는 암호화)인지 프로젝트 규칙을 확인한다. 비밀번호를 복호화 가능하게 저장하지 않는다.
