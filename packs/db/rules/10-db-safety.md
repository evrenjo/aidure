## DB 작업 안전 원칙

- **어느 인스턴스·스키마인지 먼저 확정한다.** 환경 표는 project 팩에 있다. "개발DB" 처럼 여러 곳을 가리킬 수 있는 말이면 작업하지 말고 묻는다. 이름이 겹치면 `<인스턴스>.<스키마>` 로 부른다.
- **운영 DB 에 직접 쓰지 않는다.** 운영용 SQL 은 파일로 남기고 반영은 별도 승인 절차로.
- **파괴적 변경(UPDATE·DELETE·DROP·TRUNCATE·권한 변경)** 은 같은 조건의 건수 조회나 롤백되는 시험으로 대상 수를 보고, 대상·보존 기준과 되돌릴 방법(백업·대상 행 사본)을 적은 뒤 **그 건마다 승인**받는다.
- **스키마는 프로젝트의 마이그레이션 도구(없으면 DDL 파일)로만** 바꾼다. **이미 적용된 마이그레이션은 고치거나 지우지 않고** 새 파일을 더한다.
- **호환을 깨는 변경은 확장 → 전환 → 축소** 로 나눈다. 추가는 구 코드가 깨지지 않게(nullable·기본값), 삭제·이름·타입 변경은 그 코드가 모든 환경에서 안 쓰게 된 **다음 릴리스에.**
- 큰 테이블의 DDL 은 짧은 잠금 대기 제한을 걸고, 대량 UPDATE/DELETE 는 **작은 묶음으로 나눠** 돈다.
- 값은 **바인드 파라미터로만** 넣는다. 비밀번호·접속 문자열은 어디에도 적지 않고 **출처만** 가리킨다. 운영 데이터를 다른 곳으로 옮기면 개인정보를 가린다.
- 결과·근거는 **실행한 쿼리와 건수**로 적는다. 짝 검증은 0 이 나와야 정상인 쿼리로.
