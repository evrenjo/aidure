## 데이터 반영 · 백필 · 정리 SQL · 백업

### 1. 실행 전 — 건수와 되돌릴 방법

- 같은 조건의 `SELECT count(*)`(문서 DB 는 같은 필터의 건수 조회)로 대상 수를 먼저 본다.
- 트랜잭션을 쓸 수 있으면 **실행 → 건수 확인 → 롤백** 으로 시험한다. 결과 건수를 적어 둔다.
- 파괴적 변경은 대상·보존 기준을 SQL 주석에 적고 **그 건마다 사용자 승인**을 받는다.
- **되돌릴 방법을 먼저 만든다.**
  - 작은 범위: 대상 행을 백업 테이블·파일로 떠 두고, 되돌리는 SQL 을 미리 써 둔다.
  - 운영·큰 범위: 최근 백업이 있는지, 시점 복구(PITR) 가능 범위가 작업 시각을 덮는지 확인한다. 확인 못 하면 진행하지 않고 묻는다.
- 조건이 틀리면 대상이 전부가 된다. `WHERE` 없는 UPDATE/DELETE, 조인 조건 누락을 한 번 더 본다.

### 2. 큰 데이터는 묶음으로

한 문장으로 수백만 행을 바꾸면 잠금이 길어지고 로그·복제 지연이 커지며, 실패하면 전부 되감는다.

- **키 범위(또는 마지막으로 처리한 키 다음부터)로 나눠** 묶음마다 커밋한다. `OFFSET` 으로 나누지 않는다 — 뒤로 갈수록 느려지고, 도중에 행이 바뀌면 빠지거나 겹친다.
- 나누는 기준 컬럼에는 인덱스가 있어야 한다. 유일하지 않은 컬럼으로 나누면 경계에서 무한 반복·누락이 난다 — 기본키나 유일 키로 나눈다.
- 묶음 크기는 **한 묶음이 짧게(수 초 안) 끝나는 값**으로 시작해 재며 조절한다. 행 수를 정해 두기보다 시간을 기준으로 본다.
- 묶음 사이에 쉬어 간다(복제 지연·부하를 보며). 운영 시간대를 피할 수 있으면 피한다.
- 중간에 멈춰도 **다시 돌리면 이어서 끝나게** 짠다(아직 안 바뀐 행만 고르는 조건). 진행 위치를 로그로 남긴다.
- 스키마 마이그레이션 안에서 대량 백필을 하지 않는다 — 배포가 그 시간만큼 묶인다. 별도 작업으로 돌리고, 그 결과에 기대는 코드·제약(NOT NULL 등)은 **백필 완료를 확인한 뒤** 넣는다.
- 백필 중에도 앱은 계속 쓴다. 새로 들어오는 행은 **앱이 이미 새 규칙으로 쓰고 있어야** 백필이 끝났을 때 빈틈이 없다(확장 → 전환 순서).

### 3. 멱등 · 중복 방어

- **멱등**: `NOT EXISTS` 가드, `IF NOT EXISTS`, upsert. 두 번 돌려도 결과가 같아야 한다.
- **중복 방어**: 원본에 중복이 있으면 백필이 배수로 증폭한다. 넣기 전에 키로 한 건만 고른다(윈도 함수 `ROW_NUMBER()` 등).
- 데이터 마이그레이션 코드는 **그 시점의 스키마**로 동작해야 한다. 앱의 현재 모델 클래스에 기대지 않는다.

### 4. 실행 후 — 0 이어야 정상인 검증 쿼리

짝이 맞는지를 **0 이 나와야 정상인 쿼리**로 만들어 돌리고 결과를 남긴다. 재발 감지용으로 파일에 보존한다.

```sql
-- 본문 있는데 짝(연결 행) 없음 = 0
SELECT count(*) FROM parent p
WHERE NOT EXISTS (SELECT 1 FROM child c WHERE c.parent_id = p.id);

-- 자연키 중복 = 0 (배수 조인 조기 감지)
SELECT count(*) FROM (SELECT k1, k2 FROM t GROUP BY k1, k2 HAVING count(*) > 1) x;

-- 백필 누락 = 0
SELECT count(*) FROM t WHERE new_col IS NULL AND old_col IS NOT NULL;
```

- 건수만 보지 말고 **바뀐 값이 맞는지 표본 몇 건을 눈으로** 본다(개인정보는 가린 채로).

### 5. 여러 스키마 · DB · 테넌트를 도는 SQL

- 환경 표의 **대상 전부(운영 포함)** 를 목록에 적되, **없는 스키마·DB 는 건너뛰게** 짠다. 그래야 어느 환경에 붙어 돌려도 목록이 해를 끼치지 않는다. 문법은 stack 팩 룰을 따른다.
- **목록에 적는 것과 운영에 돌리는 것은 다르다.** 헤더 주석에 대상 목록과 "운영 반영은 별도 승인" 을 적는다.
- 삭제·파괴적 변경은 환경마다 배포 시점이 다르므로 **목록 전부를 한 번에 돌리지 않는다.**

### 6. 백업 · 복구 · 덤프

- **백업이 아니라 복구가 목표다.** 복구해 본 적 없는 백업은 있다고 치지 않는다. 복구 절차·걸린 시간·확인한 행 수가 기록돼 있는지 본다.
- 백업 정책(주기·보관 기간·PITR·RPO/RTO)은 인프라 담당의 영역이다. 에이전트는 **작업 전에 그것이 있는지 확인하고, 없으면 알린다.** 백업 설정을 직접 바꾸지 않는다.
- 덤프·백업 파일은 개인정보·비밀을 담는다 → repo·공유 채널에 올리지 않고, 쓰고 나면 지운다(`packs/db/rules/40-access-and-data.md`).
- 복구는 **새 위치(별도 DB·스키마)에 먼저** 풀어 확인한 뒤 옮긴다. 운영 DB 위에 바로 덮어쓰지 않는다.
- 상세 → `packs/db/docs/backup-and-restore.md`
