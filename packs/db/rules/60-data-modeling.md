## 테이블 · 컬럼 설계

**프로젝트에 이미 정한 규칙(명명·키 타입·공통 컬럼·삭제 방식)이 있으면 그것이 먼저다.** 기존 테이블 몇 개를 열어 관례를 확인한 뒤 맞춘다.
아래는 관례가 없거나 새로 정해야 할 때의 기본값이다.

### 1. 키

- 모든 테이블에 기본키를 둔다. 기본키는 **바뀌지 않는 값**(대리키)으로 하고, 업무상 유일한 값은 별도 유일 제약으로 건다.
- 자동 증가 키는 **넉넉한 정수형(64비트)** 으로. 32비트는 다 차면 바꾸기가 매우 비싸다(여러 릴리스 작업).
- 외부에 노출되거나 여러 곳에서 만들어지는 키는 UUID 류를 쓸 수 있다. 쓰기 성능이 중요하면 시간 순 정렬되는 형식을 고른다. 프로젝트 관례를 따른다.

### 2. 타입

| 값 | 권장 | 피한다 |
|---|---|---|
| 시점 | 시간대가 붙은 형식 또는 UTC 기준 명시 | 시간대 없는 형식에 기준을 안 적음 (→ `packs/db/rules/50-transactions-and-connections.md` §5) |
| 금액·수량 | 고정 소수(`DECIMAL`/`NUMERIC`) + 통화 컬럼 | 부동 소수, DB 전용 화폐 타입 |
| 문자열 | 길이 제한이 업무 규칙이면 그 길이로. 임의로 작게 잡지 않는다 | 근거 없는 짧은 길이(나중에 늘리는 비용이 DBMS 마다 다르다) |
| 참/거짓 | 불리언(없으면 프로젝트 관례의 코드값) | 의미가 셋 이상인데 불리언 |
| 구조가 자주 바뀌는 속성 | JSON 컬럼 (검색하는 값은 따로 컬럼으로) | 조인·제약이 필요한 값을 JSON 안에 |

- NULL 은 "모름·해당 없음" 이 실제로 있을 때만 허용한다. 기본은 NOT NULL + 의미 있는 기본값.
- **유일 제약과 NULL**: 대부분의 DBMS 는 NULL 을 서로 다른 값으로 보아 유일 제약이 NULL 여러 개를 허용한다. 업무상 하나여야 하면 DBMS 의 옵션이나 부분 인덱스로 막는다.

### 3. 코드값 · enum

| 방식 | 값 추가 | 값 삭제·이름 변경 | 적합 |
|---|---|---|---|
| DB enum 타입 | 대개 가능(DBMS 마다 제약) | 어렵다 — PostgreSQL 은 값 삭제 불가, MySQL 은 테이블 변경 | 거의 안 바뀌는 작은 집합 |
| 문자열 + CHECK 제약 | 제약 교체 | 제약 교체 + 백필 | 안 바뀌는 작은 집합 |
| 코드 테이블 + 외래키 | 행 추가 | 행 비활성화 | 운영 중 늘어나는 집합, 설명·정렬·다국어가 필요할 때 |

- enum 값 이름 바꾸기는 **새 값 추가 → 코드가 둘 다 읽기 → 새 값 쓰기 → 백필 → 옛 값 제거** 순이다.
- 숫자처럼 보이는 문자열을 enum 값으로 쓰지 않는다(값과 내부 순번이 헷갈린다).

### 4. 외래키 · 인덱스

- 관계는 외래키로 건다. 앱 코드만으로 지키는 정합은 동시성·버그에 깨진다. 다른 DB·서비스로 나뉘어 걸 수 없으면 그 사실과 대신 지키는 방법을 적는다.
- **외래키 컬럼에는 인덱스를 둔다**(DBMS 가 자동으로 안 만드는 경우가 많다). 없으면 부모 삭제·갱신 때마다 자식 테이블 전체를 훑고 잠금이 커진다.
- `ON DELETE` 는 의도대로 고른다 — 부모와 함께 사라져야 하면 CASCADE, 독립적이면 SET NULL, 지우면 안 되면 RESTRICT. 연쇄 범위가 큰 CASCADE 는 삭제 한 번이 대량 삭제가 된다.
- 인덱스는 **실제 쿼리의 실행 계획으로 필요를 확인한 뒤** 만든다. 복합 인덱스는 앞쪽 컬럼이 없는 조건에는 잘 안 쓰인다. 비슷한 인덱스가 이미 있는지 먼저 본다. 쓰이지 않는 인덱스는 쓰기만 느리게 한다.
- 제약·인덱스에는 이름을 붙인다.

### 5. 삭제 방식 — 소프트 삭제는 대가가 있다

| | 물리 삭제 | 소프트 삭제(`deleted_at`·`is_deleted`) | 삭제 보관 테이블 |
|---|---|---|---|
| 되살리기 | 백업에서 | 쉽다(값 되돌림) | 보관 테이블에서 옮김 |
| 조회 조건 누락 위험 | 없음 | **모든 쿼리에 조건 필요** — 빠지면 지운 행이 보인다 | 없음 |
| 외래키·유일 제약 | 정상 동작 | 지운 행이 제약을 계속 붙잡는다(같은 키 재생성 불가 등) | 정상 동작 |
| 삭제 의무 이행 | 쉽다 | 별도 정리 작업 필요 | 보관 테이블만 정리 |

- 프로젝트가 이미 소프트 삭제를 쓰면 **모든 조회·조인·유일 제약에 삭제 조건이 들어 있는지** 새 쿼리마다 확인한다(부분 유일 인덱스 등).
- 새로 정해야 하면 되살리기 요구가 실제로 있는지 묻는다. 없으면 물리 삭제, 있으면 보관 기간을 정한 소프트 삭제나 보관 테이블.
- 삭제에는 DB 밖 부수 효과(파일·외부 시스템)가 따를 수 있다. 값만 되돌린다고 되살아나지 않는다.

### 6. 공통 컬럼 · 감사

- 생성·수정 시각과 주체(`created_at`·`updated_at`·`created_by`·`updated_by` 류)는 프로젝트 관례를 따르고, **한 곳에서** 채운다(ORM 감사 기능·DB 기본값·트리거 중 하나). 경로마다 손으로 채우면 빠진다.
- 대량 SQL·백필로 바꿀 때 수정 시각·주체를 어떻게 채울지 정한다(일괄 작업 표시 등).
- 공통 컬럼은 "마지막 변경" 만 남긴다. **누가 무엇을 바꿨는지의 이력**이 필요하면 감사 테이블·이력(temporal) 테이블·변경 로그를 따로 둔다. 감사 기록에도 개인정보 규칙이 적용된다.
