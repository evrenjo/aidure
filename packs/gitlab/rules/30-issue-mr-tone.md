## 이슈 · MR 본문 — 확인 요청 어조

남이 읽는 산출물은 **판정을 통보하지 않고 확인을 요청**한다. 읽는 사람은 그 코드를 짠 사람이다.
판정조로 쓰면 사실이 맞아도 방어적으로 읽히고, 우리가 원하는 확인·후속 조치가 늦어진다.

### 3단 구성

1. **발견 경위** — 무슨 작업을 하다가 보게 되었는지 ("~를 보던 중 함께 살펴보게 되었습니다")
2. **분석 결과** — 대조해 보니 어떻더라 ("~로 되어 있는 것으로 보입니다")
3. **확인 요청** — ("의도된 설계인지, 반영이 필요한 부분인지 확인 부탁드립니다")

### 표현

| 쓰지 않는다 | 대신 |
|---|---|
| 없다 / 누락 / 결함 / 틀렸다 | ~가 들어 있지 않은 곳이 있습니다 · 확인이 필요해 보입니다 |
| 상태 `미해결` | 상태 `확인 요청` |
| 제목·파일명에 판정 (`~누락`, `xxx-missing-yyy.md`) | 주제 + `확인 요청` (`xxx-yyy-check.md`) |

- **톤만 낮추고 근거는 줄이지 않는다** — 대조표·SQL·실측 수치·`파일:라인` 은 그대로. 완곡하되 모호하지 않게.
- 사람·지시를 언급하지 않는다. "누가 했다" 가 아니라 코드·파일 기준으로 적는다.
- GitLab 이슈 본문은 2~3단락, 상세는 맨 끝 링크 한 줄로 문서에 위임한다.

### 미해결 확인 항목은 4칸을 채운다

| 칸 | 내용 |
|---|---|
| **질문** | 물음표로 끝나는 한 문장. 무엇을 정해 달라는지가 그대로 드러나게 |
| **누가 답하나** | 고객 / 우리 / 그 코드 담당 |
| **답에 따른 조치** | `Yes 면` … / `No 면` … — 손댈 파일·작업량까지 |
| **지금 상태** | 미구현 · 임시 조치 · 그대로 두면 생기는 영향 |

- "…가 사라진다", "…를 없앴다" 처럼 **요청 문장 없이 서술로 끝나는 항목은 확인 요청이 아니다.**
- 결정된 항목은 목록에서 빼 `종결된 확인 항목` 으로 옮기고 **결정 한 줄 + 날짜**만 남긴다.
