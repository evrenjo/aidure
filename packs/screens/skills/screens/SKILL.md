# screens: 화면설계서 작성

양식과 뷰어는 킷이 준다. 이 스킬은 내용을 채우는 순서다. 각 단계에서 정할 것은 사용자에게 하나씩 묻는다.

| 파일 | 내용 |
|---|---|
| `packs/screens/assets/storyboard/template.html` | 장 양식 견본 5장: 표지 · 변경 이력 · 메뉴 구조 · 정책 · 화면 |
| `packs/screens/assets/storyboard/storyboard.css` · `src/` | 양식 스타일 · 뷰어 (문서 사이트를 만들 때 `assets/storyboard/` 로 들어간다. 기획 repo 에 따로 두지 않는다) |
| `packs/core/bin/docs-site.js` | `aikit docs build` : 기획 repo 의 md 와 장 HTML 로 문서 사이트(`<기획 repo>/docs-site/`)와 근거 색인(`<기획 repo>/docs-site/assets/ids.json`)을 만든다 |
| `packs/screens/bin/check-screens.js` | `aikit screens check` : 장의 근거 ID · 화면 ID 중복 · 기능 ID 누락 |

## 1. 진행 방식 합의

먼저 아래를 정한다. 기획 repo 에 이미 정해 둔 것이 있으면 따른다.

- **대상**: 어떤 화면 범위인가 (웹 관리 화면 · 모바일 앱 · 데스크톱 등).
- **근거 문서**: 요구사항 · 기능정의 · 설계 문서가 어디에 있는가. 화면은 기능 ID(없으면 요구사항 ID)를 근거로 그린다. 근거 없이 화면 요소를 지어내지 않는다.
- **ID 체계**: 화면 ID 꼴(예: `SCR-<영역>-<번호>`)과 기능 ID 머리말. 기능 ID 머리말은 `workspace.json` 의 `vars.screens.functionIds` 에 적는다 (누락 검사가 쓴다).
- **색**(물을 때만): 기본 인디고. 바꾸려면 `workspace.json` 의 `vars.screens.theme` 에 `blue` · `teal` · `orange` · `rose` 중 하나.
- **산출물 위치**: 기획 repo 의 화면 폴더(뼈대 기본 `02-screens/`). **설계서 하나 = 장 파일 하나**(예: `<화면 폴더>/screens.html`)가 기본이고, 영역 · 메뉴 구분은 장의 `data-group` 으로 나눈다. 파일을 나누면 뷰어 · 장 선택 · 썸네일이 파일마다 따로 생겨 설계서 전체를 한 번에 넘겨 볼 수 없다. 대상이 전혀 다른 설계서(예: 관리자 웹과 모바일 앱)만 파일을 나눈다.
- **순서**: 공통(메뉴 구조 · 화면 정책) → 영역별 화면.

## 2. 화면 정책

화면 공통 규칙(접근 · 오류 · 상태 표시 · 숫자 · 날짜 · 모바일 · 접근성 등)을 md 로 먼저 정한다 (예: `03-policies/` 또는 화면 폴더의 `policy.md`).

- 규칙 하나에 ID 하나 (`### POL-…` 제목 또는 표 첫 칸). 결정이 필요한 것은 선택지로 묻고, 정해지면 결정 ID 를 단다.
- 정책 장(④)은 이 md 를 요약한 것이다. 비고 칸에 확정이면 근거 ID, 아니면 「결정 대기」.

## 3. 화면 목록

화면 폴더의 `README.md` 에 화면 목록 표를 둔다. 첫 칸이 화면 ID 라야 검사가 장과 대조한다.

| 화면 ID | 화면 | 경로(메뉴) | 기능 ID | 모바일 |
|---|---|---|---|---|

- 기능정의의 기능 ID 를 모두 대조한다: 기능마다 화면이 있거나, 화면이 없는 기능이면 「화면 없음」 과 이유를 적는다.
- 진행 방식이 스프린트(AGENTS.md 「진행 방식」)이면 이번 스프린트(`handoffs/PLAN.md` 「이번 스프린트」) 기능의 화면만 그린다. 나머지 기능은 한 행에 모아 「다음 스프린트」 로 적는다 (검사가 세지 않는다). 메뉴 구조에는 나중에 붙일 메뉴 자리만 남긴다.
- 화면 ID 는 한번 붙이면 바꾸지 않는다. 없앤 화면은 결번으로 남긴다.

## 4. 화면별 장 작성

`template.html` 을 복사해 시작하고, 장은 같은 파일에 이어 붙인다. 장 하나 = `<section class="sheet" id="<화면 ID>" data-group="<큰 구분>" data-label="<화면 ID> <화면 이름>">`.

- 메타 표: Page Title · Screen ID · Date / Screen Path · Related ID(기능 ID) · Author(역할). Related ID 는 화면 목록과 같게.
- 와이어프레임은 부품 클래스(`wf` · `wf-img` · `wf-input` · `wf-btn` · `wf-link` · `wf-bar` · `wf-table` · `area-label`)로 그리고, 설명할 곳에 번호 마커 `mk` 를 단다.
- Description: 마커 번호 순서대로 결론 한 줄 + 근거 ID(설명 아래 `<ul>`). 아래 「Description 쓰는 법」 을 따른다. Check Point: 놓치기 쉬운 조건, 아직 정하지 않은 것은 `<p class="tag-todo">미정: …</p>`.
- 맨 아래 근거 줄(`<div class="refs">근거: …</div>`)에 이 장의 근거 ID 를 모은다. 「VS-ADM-04 · 05」 처럼 줄여 써도 각각 링크된다.
- 여러 문서에 같은 번호가 있는 ID(문서마다 매기는 결정 번호)는 `data-area="<폴더나 파일 이름 조각>"` 으로 먼저 열 문서를 정한다.
- 사람 이름 대신 역할로 쓴다.
- **내부 정보**: 개발자가 알면 되는 것은 뷰어의 기본 보기 · 인쇄에서 숨고 「내부 정보」 버튼(I 키)으로 보인다. Check Point(`<h3>Check Point</h3>` + `.check`) · 근거 줄(`.refs`) · 마커별 근거 ID(Description 줄 안의 `<ul>`)는 저절로 내부 정보다. 그 밖에 장에 따로 둔 개발용 블록(예: 사용 API · 저장 필드)은 `class="sb-dev"` 를 붙인다. 기본 보기에는 와이어프레임 · 메타 표 · 마커 설명 문장이 남으므로, 화면을 이해하는 데 필요한 내용은 설명 문장에 쓴다. 마커에 마우스를 올리면 그 줄의 근거 ID 가 잠깐 보인다.
- **한 장 = A4 가로 한 쪽.** 기본 보기(내부 정보 제외)가 장 높이(885px) 안에 들어가게 쓴다. 넘치면 뷰어가 장 위에 「⚠ 한 쪽 넘침」 · 썸네일에 ⚠ 를 띄우고(내부 정보를 켜 두어도 기본 보기 높이로 잰다), 인쇄는 그 장만 작게 줄인다. 내부 정보를 켜고 인쇄하면 함께 인쇄되고 그만큼 더 줄어든다. 넘치면 이 순서로 줄인다:
  1. 설명은 마커마다 결론 한 줄 (「Description 쓰는 법」).
  2. 결정 경위 · 날짜 · 대안 비교는 정책 · 결정 문서로 옮기고 Check Point 에는 결론 한 줄 + 결정 ID 만 남긴다. 개발용 블록은 `sb-dev` 로 내부 정보에 둔다.
  3. 그래도 넘치면 장을 나눈다: 같은 화면의 다음 장은 `id="<화면 ID>-2"` · `data-continues="<화면 ID>"` · `data-label="<화면 ID> <화면 이름> (계속)"` (검사가 화면 목록 대조에서 뺀다), 메타 표는 그대로 두고 와이어프레임은 그 장에서 설명하는 부분(모바일 · 상태별 모습 등)만 그린다.

### Description 쓰는 법

읽는 사람은 화면을 처음 보는 사람이다. 줄마다 **이 자리에 무엇이 있고 무엇을 하는지**의 결론만 쓰고, 자세한 내용은 근거 ID 를 눌러 본다.

- 한 줄 60자 안. 「이름: 무엇 · 무엇」 꼴로 쓴다.
- 쓰지 않는다: 날짜 · 결정 번호 · 바뀐 경위(「…으로 바꿈」 · 「추가됨」 · 「사용자 결정」), 괄호 속 세부 조건 나열, 값 범위 · 색 · 개수 같은 세부 규칙. 이것들은 기능정의 · 정책 · 결정 문서에 두고 줄 아래 근거 ID(기능 ID · 정책 ID · 결정 ID)로 잇는다.
- 근거 문서에 없는 세부 내용이면 지우기 전에 그 기능 · 정책 문서에 먼저 옮긴다. 화면설계서에만 남은 규칙이 없어야 한다.
- `aikit screens check` 가 60자 넘음 · 날짜 · 결정 경위가 든 줄을 ⚠ 로 알린다.

| 나쁜 예 | 좋은 예 (근거 ID 는 줄 아래 `<ul>`) |
|---|---|
| 시장 띠: 지수 카드 3개(코스피 · 코스닥 · 코스피200 선물 값 · 등락 · 당일 미니 선, 선물은 2026-10-16 사용자 결정으로 추가) / 테마 TOP 5 가로 막대(…) | 시장 띠: 지수 · 테마 TOP 5 · 시장 수급 카드 |
| 보유 종목 카드: [내 계좌 \| 가상 계좌] 전환, 마지막 선택을 계정 화면 설정에 기억(FN-…, 결정 89), 기본 접힘, … | 보유 종목 카드: 계좌별 보유 종목과 비중 |

**이미 쓴 설계서 다듬기**: `aikit screens check` 의 ⚠ 줄을 위 규칙으로 고친다. 줄마다 (1) 세부 내용이 근거 문서에 있는지 보고 없으면 옮기고, (2) 결론 한 줄로 줄이고, (3) 근거 ID 를 줄 아래에 둔다. 다 고치면 `aikit docs build` 로 다시 만들고 넘침 장도 함께 본다.

## 5. 문서 사이트 반영 · 검사

```
aikit docs build <기획 repo>      # docs-site/ 와 근거 색인을 다시 만든다 (md 나 장을 고칠 때마다)
aikit screens check <기획 repo>   # ✖ 가 없어야 한다
```

- Pages 를 켠 repo(`aikit docs pages`)는 `docs-site/` 를 커밋한다. 기획 repo 의 pre-commit 이 md 와 `docs-site/` 가 어긋나면 막는다.
- 문서 사이트 메뉴에는 장 파일이 따로 나오지 않는다. 화면설계 묶음의 첫 항목(화면 폴더 README 쪽, 없으면 폴더 쪽)이 개요가 되어 맨 위에 장 수 · 묶음별 화면 목록 · 「설계서 보기」 를 보이고, 묶음 제목 옆 ▶ 버튼도 설계서로 간다. 뷰어의 「← 문서」 는 그 개요로 돌아간다.
- 확인은 `docs-site/` 를 브라우저로 연다 (`file://` 로도 열리지만 근거 패널은 http 서버에서 확실하다: `aikit docs serve`).
- 뷰어에서 「⚠ 한 쪽 넘침」 장이 없는지 본다 (썸네일의 ⚠). 있으면 4단계의 순서로 줄이고 다시 만든다. 이 검사는 브라우저에서만 된다 (`aikit screens check` 는 높이를 재지 못한다).
- 결과를 사용자에게 알릴 때 장 수 · 화면 수 · 검사 결과(✖ · ⚠ 줄) · 한 쪽 넘침 장를 그대로 옮긴다.
