## 코드 변경 작업 상세

상시 룰 "작업 원칙" 의 풀이다. 순서는 **이해 → (필요하면) 계획 → 구현 → 검증 → 보고**.

### 1. 이해 — 고치기 전에 읽는다

- 대상 파일, 그 호출부, 같은 일을 하는 기존 구현, 관련 테스트를 읽는다. 테스트는 사용법과 기대 동작을 가장 잘 보여 준다.
- 루트에서 대상 폴더까지의 `README`·`AGENTS.md`·`CONTRIBUTING` 을 본다 — 하위 폴더의 지침이 더 가깝다.
- 모르는 이름은 정의를 찾아 확인한다. 라이브러리·프레임워크가 이 프로젝트에 이미 있는지, 어떻게 쓰이는지 확인하고 쓴다 — 기억한 API·명령을 옮겨 쓰지 않는다.
- 이슈를 맡았으면 같은 문제를 다루는 열린 변경(PR)이 있는지 먼저 본다.
- 조사 범위를 정해 둔다. "무엇을 알아야 결정할 수 있는가" 가 채워지면 읽기를 멈춘다. 큰 파일은 검색으로 위치를 찾고 필요한 범위만 읽는다.

### 2. 계획 — 언제 먼저 보이나

| 먼저 계획을 보인다 | 바로 한다 |
|---|---|
| 여러 파일·여러 repo 에 걸친다 | 한 문장으로 설명되는 수정 (오타·로그 한 줄·이름 하나) |
| 접근이 여럿이고 결과가 갈린다 | 위치와 방법이 요청에 이미 정해져 있다 |
| 공개 API·스키마·데이터·설정을 바꾼다 | |
| 익숙하지 않은 영역이다 | |
| "어떻게 하나요?" 라고 물었다 (설명이 먼저) | |

계획에는 **영향 범위 · 할 일(파일 단위) · 검증 방법 · 안 할 것과 이유**를 적는다. 큰 변경은 따로 검증할 수 있는 단계로 나누고, 먼저 넣을 수 있는 가장 작은 단계를 찾는다. 진행 중 계획이 바뀌면 바뀐 점을 알린다.

### 3. 멈추고 물을 때 · 가정하고 갈 때

**멈추고 묻는다** — 이 중 하나일 때만:

- 사용자만 정할 수 있는 결정 (정책·우선순위·범위)
- 되돌릴 수 없는 행동 (상시 룰 「보안·안전」 의 목록)
- 필요한 자격 증명·환경이 없다
- 해석이 여럿이고 결과(데이터·동작·공개 계약)가 달라진다 — 해석들을 나란히 보이고, 조용히 하나를 고르지 않는다
- 요청의 전제가 사실과 다르다 — 그 위에 쌓기 전에 말한다

**가정하고 진행한다** — 코드·문서로 확인할 수 있거나 되돌리기 쉬운 선택. 먼저 더 읽어서 풀 수 있으면 읽는다. 가정은 보고에 한 줄로 적는다.
더 단순한 방법이 있으면 진행 전에 말한다.

### 4. 관례 — 주변 코드가 기준

- 이름·폴더 구조·오류 처리·로그·타입 표기·테스트 방식·주석 밀도는 **같은 모듈의 기존 코드**에 맞춘다. 내 선호와 달라도 맞춘다.
- 새 헬퍼·유틸을 만들기 전에 같은 일을 하는 것을 찾는다. 비슷한 코드를 복사해 늘리지 않는다. 반대로 한 곳에서만 쓰는 한두 줄짜리 헬퍼는 만들지 않는다.
- 아키텍처 경계(레이어·모듈 의존 방향)를 넘지 않는다. 넘어야 하면 먼저 묻는다.
- 포맷·린트는 프로젝트의 포매터·린터가 정한다. 편집한 파일은 그 도구로 정리한다.

### 5. 범위 — 바뀐 줄마다 요청으로 거슬러 올라가야 한다

- 요청과 관계없는 리팩터링·이름 변경·포맷 정리·주석 손질·의존성 올리기를 섞지 않는다. 리뷰어가 의도한 변경을 찾기 어려워지고, 되돌릴 때 함께 사라진다.
- 지금 필요한 문제만 푼다 — 올지도 모를 요구를 위한 설정값·추상화·확장 지점·불가능한 경우의 방어 코드를 만들지 않는다.
- **범위를 지키는 것과 구현을 억지로 작게 만드는 것은 다르다** — 요청을 제대로 끝내는 데 필요한 변경은 한다.
- 내 변경 때문에 안 쓰이게 된 것은 지운다. 원래 있던 죽은 코드·다른 문제는 지우지 말고 알린다 (제시된 문제를 푸는 데 꼭 필요하면 함께 고치고 그 사실을 적는다).
- 한 변경(커밋·PR)은 한 목적. 섞여야 하면 나눌 수 있는지 먼저 본다.

### 6. 남의 변경 존중

- 작업 트리에 이미 있던 수정은 사용자 것이다 — 되돌리거나 덮어쓰지 않는다. 같은 줄을 건드려야 하면 멈추고 묻는다.
- 사람이 쓴 PR 설명·기록 구역은 고치지 않는다. 템플릿이 있으면 그 구조를 따른다.

### 7. 공개 계약 — 하위 호환

- 공개 API·함수 시그니처·CLI 옵션·설정 키·기본값·파일 형식·DB 스키마·이벤트 형식을 바꾸면 모든 소비처를 찾는다 (`.agents/rules/core--30-change-impact.md`).
- "지난주에 이걸 쓴 사람의 코드가 깨지는가?" 를 묻는다. 이름 변경·삭제는 옛 이름을 한동안 받아 주는 방법이 있는지 먼저 보고, 인자 순서·필수 여부·반환 타입을 조용히 바꾸지 않는다. 깨지는 변경이면 보고와 변경 기록에 분명히 적는다.

### 8. 생성물·의존성

- 자동 생성 파일(API 클라이언트·스텁·스키마 산출물·스냅샷·빌드 산출물·잠금파일)은 **입력(스키마·원본·템플릿·설정)을 고치고 생성기를 다시 돌린다.** 고치기 전에 그 줄이 생성된 것인지 확인한다 (파일 머리의 "generated / do not edit", 생성 스크립트).
- 의존성 추가·버전 변경은 `.agents/rules/core--27-security.md` 의 확인표를 채워 근거로 묻는다.

### 9. 오류 처리·코드 품질 (언어와 무관한 것만)

- 넓은 범위로 예외를 삼키지 않는다. 처리할 수 있는 오류만 잡고, 나머지는 호출자에게 올린다. 호출자가 전파를 기대하는지 삼키기를 기대하는지 확인한다.
- 오류 메시지는 무엇이 왜 실패했는지와 실제 값을 담는다 ("문제가 발생했습니다" 로 끝내지 않는다). 예외 메시지 문자열을 파싱해 분기하지 않는다.
- 타입 시스템을 우회하는 표기(`any`·강제 캐스트·null 단언)는 이유가 있을 때만. 그 프로젝트의 타입 엄격도를 따른다.
- 같은 결과면 더 짧고 단순한 구현을 고른다.

### 10. 문서·주석

- 동작이 바뀌면 README·참고 문서·사용법·변경 기록·예시 설정·해당 지침 파일을 같은 변경에서 고친다. 구체적인 기존 설명을 일반론으로 바꿔 쓰지 말고 고쳐 쓴다.
- 주석은 코드만 봐서는 알 수 없는 **이유·불변식·함정**만 적는다. 코드를 다시 말하는 주석은 쓰지 않는다 ("이 주석을 지우면 독자가 무엇을 잃는가?").
- 주석에 변경 이력·대화 맥락("이전에는 …", "이제 …", "요청에 따라 …")·검토자에게 하는 말·"현재/오늘" 같은 시점 표현을 쓰지 않는다. 몇 달 뒤 이 대화를 모르는 사람이 읽는다.
- 내가 바꾸지 않는 코드의 주석은 손대지 않는다. 코드를 옮길 때 기존 주석은 유지한다.
- 긴 배경·근거는 주석이 아니라 이슈 문서·커밋 설명으로. 문서를 옮기거나 지울 때는 `.agents/rules/core--41-context-detail.md` 를 따른다.

### 11. 마무리

- 임시 스크립트·디버그 출력·캡처·덤프는 OS 임시 폴더(또는 프로젝트가 정한 gitignore 폴더)에 두고 끝나면 지운다. 디버그 출력이 코드에 남지 않게 한다.
- 띄운 서버·프로세스는 내가 띄운 것만 정리한다.
- 검증과 보고는 `.agents/rules/core--21-verification.md`.
