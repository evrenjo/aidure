## 확인 요청 글 — 이슈 문서 · 이슈 · MR 본문

이 룰은 **글의 톤**을 정한다. 어디에 쓸지는 정하지 않는다: 위치는 사용자가 말한 곳이고, 말하지 않았으면 대화로 답한다. 이슈 repo 에는 이 프로젝트의 이슈만 둔다 (다른 프로젝트·킷에 전달할 글은 아니다).

읽는 사람은 그 코드를 만든 사람일 수 있다. "누락 / 결함 / 틀렸다" 로 쓰면 사실이 맞아도 취조하는 글이 되고
받는 쪽이 방어적으로 읽는다. 원하는 것은 판정이 아니라 **확인과 후속 조치**다.

### 3단 구성

1. **발견 경위** — 무슨 작업을 하다 보게 되었는지 ("~를 보던 중 함께 살펴보게 되었습니다")
2. **분석 결과** — 대조해 보니 어떻더라 ("~로 되어 있는 것으로 보입니다")
3. **확인 요청** — ("의도된 설계인지, 반영이 필요한 부분인지 확인 부탁드립니다")

### 표현

| 쓰지 않는다 | 대신 |
|---|---|
| 조건이 **없다** / **누락** / **결함** | 조건이 **들어 있지 않은 곳이 있습니다** |
| 정합 X / **불일치** / **틀렸다** | **확인이 필요해 보입니다** |
| 상태 `미해결` | 상태 `확인 요청` |
| 제목에 판정 (`~누락`) · 파일명 `xxx-missing-yyy.md` | 제목은 주제 + `확인 요청` · 파일명 `xxx-yyy-check.md` |

- 단정형이 아니라 추정·제안형. **톤만 낮추고 근거는 줄이지 않는다** — 대조표·쿼리·수치·`파일:라인` 은 그대로 싣는다. 완곡하되 모호하지 않게.
- 사람·지시를 언급하지 않는다 — "누가 했다" 가 아니라 코드·파일 기준으로만.
- 이슈 트래커 본문은 2~3단락, 상세는 끝에 문서 링크 한 줄로.

### 확인 항목은 무엇을 판단해 달라는지가 문장으로 드러나야 한다

미해결 항목은 4칸을 채운다.

| 칸 | 내용 |
|---|---|
| **질문** | 물음표로 끝나는 한 문장 |
| **누가 답하나** | 요청자 / 우리 / 그 코드 담당 |
| **답에 따른 조치** | `Yes 면` … / `No 면` … — 손댈 파일·작업량까지 |
| **지금 상태** | 미구현 · 임시 조치 · 그대로 두면 생기는 영향 |

- "…가 사라진다", "…를 없앴다" 처럼 근거 서술로 끝나고 요청이 없는 항목은 확인 요청이 아니다.
- 결정된 항목은 목록에서 빼 `종결된 확인 항목` 으로 옮기고 **결정 한 줄 + 날짜**만 남긴다.
