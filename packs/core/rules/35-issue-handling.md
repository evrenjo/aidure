## 이슈·티켓 처리 (모든 유형 공통)

구축 중 QA·UAT 지적이든 운영 중 장애든, 이슈 한 건은 같은 방식으로 처리한다. 절차는 `ticket` 스킬.
**결함 · 장애 · QA·UAT 지적을 처리할 때만 해당한다.** 기능 개발(특히 초반 구축)은 티켓 없이 하고, 기록은 기능·화면 이름으로 남긴다.

- **근거는 티켓이다.** 이슈 번호를 브랜치·커밋·보고에 붙인다. 이슈인데 티켓이 없으면 먼저 티켓으로 만들지 묻는다.
- **기록은 티켓 이름의 작업별 기록**(`handoffs/<id>/topics/<티켓>.md`)에 남긴다. 기존 기능 기록과 같은 일이면 그 기록의 `관련:` 에 티켓을 더해 이어 쓴다.
- **최소 변경.** 그 이슈를 해결하는 데 필요한 것만 고친다. 작업 중 발견한 다른 문제는 고치지 않고, 끝에 "별도 티켓 후보" 로만 적는다.
- **재현 전에 고치지 않는다.** 순서는 영향 범위 → 재현 → 원인 확정 → 수정 → 검증 → 조치 보고. 재현하지 못하면 멈추고 보고한다.
- **조치 보고는 다섯 칸이다**: 현상 / 원인 / 조치 / 영향 범위 / 재발 방지. 원인을 확인하지 못했으면 "추정" 으로 적는다.
- 이슈를 기록하는 repo(kind: `issues`)가 있으면 조치 보고를 거기에도 남긴다.
