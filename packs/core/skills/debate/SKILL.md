# debate: 여러 모델 토론

평소 작업은 역할 모델 하나(리뷰는 다른 회사 모델 하나)로 한다. 토론은 **요청할 때만** 돈다. 모델 수 × 회차만큼 비용 · 시간이 든다 (보통 평소 리뷰의 5~7배).

> 근거: 같은 모델끼리의 토론은 다수결로 끝나 효과가 작고, 다른 회사 모델을 섞을 때 정확도가 오른다 (arXiv 2502.08788 · 2410.12853 · 2601.05746).

## 1. 언제 제안하는가

- 사용자가 토론 · 여러 모델 · 다른 모델 의견을 말하면 바로 2절로.
- 결과가 마음에 안 든다 · 맞는지 모르겠다 · 다시 봐 달라는 뉘앙스면 **고치기 전에** 한 줄로 제안하고 묻는다. 「다른 모델 2~3개가 따로 보고 서로 반박하는 토론으로 확인할까요? (약 N분 · 평소의 몇 배 사용량)」
  사용자가 원하지 않으면 평소대로 고친다. 같은 대화에서 거절했으면 다시 권하지 않는다.
- 쓰지 않는 때: 사실 하나 확인 · 명령 실행 결과처럼 답이 정해진 것, 사용자가 빨리 끝내길 원할 때.

## 2. 패널 고르기: 쓸 수 있는 모델에서 작업에 맞게

```bash
node packs/core/bin/debate.js models --task code     # code | design | docs
```

설치된 CLI · 이 PC 설정(kedovi ai) · 로그인 요금제로 쓸 수 있는 모델과 강점 점수(LiveBench), 패널 예시가 나온다. 리더(지금 세션)가 작업을 보고 고른다.

| 기준 | 내용 |
|---|---|
| 다른 회사 | 꼭 하나 이상 넣는다. 다른 회사 CLI 가 없으면 같은 회사 다른 모델로 하되 그 한계를 사용자에게 알린다 |
| 작업 강점 | 코드 = 에이전트 코딩 · 코딩, 설계 · 원인 분석 = 추론 · 데이터 분석, 기획 · 문서 = 언어 · 지시 따르기 |
| 리더와 다르게 | 리더 모델과 같은 모델은 되도록 빼거나 관점을 달리 준다 |
| 비용 | 가장 비싼 급(API $10 이상)은 하나만. 요금제가 빠듯하면 2개 · 낮은 effort |
| 관점 (선택) | 범위가 넓으면 모델마다 관점을 나눈다: 정확성 · 보안 · 성능 · 사용자 흐름 · 반대 역할(일부러 약점을 찾는다) |

역할은 작업에 맞춘다: 코드 리뷰 `reviewer`, 설계 `architect`, 요구 · 기획 `analyst`. 패널과 예상 시간 · 사용량을 한 줄로 알리고 확인받은 뒤 시작한다.

## 3. 실행

```bash
node packs/core/bin/debate.js start --panel codex:gpt-6.1-sol:high,claude:opus:high:보안 --role reviewer --topic "주문 탭" <<'EOF'
<작업 지시서: 무엇을 · 어디를(repo · 파일 · 문서 ID) · 무엇이 쟁점인지 · 검사: <명령> 통과>
EOF
node packs/core/bin/debate.js wait <토론 id> --round   # 회차가 끝날 때마다 돌아온다. 끝날 때까지 되풀이
```

> Codex: 샌드박스가 네트워크를 막아 `start` 가 멈춘다(종료 코드 4). `start` 명령만 샌드박스 밖 실행 승인을 요청해 다시 실행한다. `wait` · `status` 는 샌드박스 안에서 된다.

### 사회자처럼 중계한다

토론은 백그라운드 CLI 라 사용자 화면에 안 보인다. 리더가 사회자로 진행을 전한다.

1. 시작하면 한 줄로 알린다: 패널 · 최대 회차 · 예상 시간, 그리고 「다른 터미널에서 `kedovi debate watch <id>` 로 모델별 주장 · 판정을 실시간으로 볼 수 있다」.
2. `wait <id> --round` 가 돌아올 때마다 사용자에게 몇 줄로 중계하고 다시 부른다. 끝날 때까지 한 번에 기다리지 않는다.
   - 1차 끝: 모델별 주장 수와 블로커 한두 개, 겹친 주장.
   - 2차부터: 합의 · 갈림 수, 갈린 주장과 누가 어느 쪽인지 한 줄씩, 빠진 모델, 다음 회차에서 볼 것.
   - 회차 중간에 시간이 다 되어 돌아왔으면: 끝난 모델 · 아직 도는 모델 한 줄.
3. 중계는 전달이다. 판정(4절)은 끝난 뒤에 한다.

- 지시서가 전부다. 패널은 대화를 모른다. 리뷰 역할은 `검사:` 줄이 필요하다 (리뷰 전 검사).
- 회차: 1차 따로 보기 → 2차 이름을 가린 주장 목록에 동의 · 반대(근거 필수, 근거 없는 동의는 보류) + 놓친 것 → 3차부터 갈린 주장만. 모두 판정이 맞으면 일찍 끝난다. `--rounds` 로 최대 회차(기본 3).
- 모델이 실패하면(사용량 한도 · 로그인) 다른 모델로 몰래 바꾸지 않고 「빠진 모델」로 적는다. 2개 미만이 되면 멈춘다.
- 읽기 전용이다. 패널은 파일을 고치지 않는다.

## 4. 결과 맞추기: 다수결로 받아쓰지 않는다

결과는 합의 · 갈림 · 기각 · 한 모델만으로 나온다. 모두 **주장**이다.

1. 합의도 블로커는 파일:줄을 직접 열어 확인한다 (모델들이 같은 착각을 할 수 있다).
2. 갈림은 양쪽 근거를 나란히 놓고 직접 확인해 판정한다. 판정이 안 되면 사용자에게 선택지로 묻는다.
3. 한 모델만 낸 것도 버리지 않는다. 확인되면 가장 쓸모 있는 발견이다.
4. 고치는 것은 사용자가 요청할 때만.
