# architecture: 시스템 구성도 (단계별 · 서버 사양 포함)

양식은 킷이 준다 (`packs/core/assets/architecture/template.md`, 기획 repo 뼈대에는 `<기획 repo>/10-system/architecture.md` 로 들어 있다. 옛 뼈대면 그 repo 의 설계 폴더). 이 스킬은 내용을 채우는 순서다. 정할 것은 사용자에게 **하나씩** 묻고, 권장안을 첫째 선택지로 둔다. 문서 사이트(`aidure docs build`)가 mermaid 블록을 그림으로 그린다 (확대 · 새 창).

## 1. 근거 모으기 (지어내지 않는다)

| 무엇 | 어디서 |
|---|---|
| 서비스 목록 · 역할 | 범위 · 아키텍처 결정 문서, 기능정의, 코드 repo 목록(`workspace.json` 의 `repos`) |
| DB · 스키마 | 데이터 설계 정의서(「### 스키마.테이블」, datamodel 스킬) · 엔티티 목록 |
| 미들웨어 · 오픈소스 (캐시 · 메시지 큐 · 검색 등) | 결정 문서, 코드 repo 의 설정 · 의존성 파일(docker-compose · 빌드 파일) |
| 외부 서비스 | 요구사항 · 연동 문서 |
| 서버 사양 · 위치 | 인프라 환경 표(infra 팩 `environment-table-template.md` 양식), 사용자 |

근거가 없는 구성 요소 · 사양은 그리지 않고 「확인 필요」 로 묻는다. 사양은 예상 부하(동시 사용자 · 일일 건수 · 데이터 증가량)를 근거 칸에 적는다. 부하 수치의 정본은 규모 문서(`<기획 repo>/00-overview/scale.md`, 없으면 `packs/core/assets/scale/template.md` 로 만든다)이고, 비었으면 먼저 묻고 거기 채운다. 단계를 나누는 이유(1차는 작게, 2차에서 분리)도 이 수치로 적는다.

## 2. 단계 정하기

- 단계는 「끝까지 동작하는 최소 구성」 부터 시작한다 (1차). 2차부터는 늘리는 이유(부하 · 분리 · 이중화 · 비용)를 한 줄로 적는다.
- 진행 방식이 스프린트면 단계를 스프린트 · 릴리스와 맞춘다. 로드맵이나 범위 결정에 단계가 이미 있으면 그대로 쓴다.

## 3. 그리기 규칙

- **구성도는 mermaid 로 쓴다.** 상자 · 화살표 문자로 그린 ASCII 그림은 쓰지 않는다 (`aidure docs build` 가 ⚠ 로 알린다).
- 단계마다 그림 하나. 한 그림에 노드가 20개를 넘으면 영역(예: 수집 · 매매 · 알림)으로 나눈다.
- 계층 순서: 사용자 · 외부 → 서비스 → 미들웨어 → 저장소. 서버(호스트)는 `subgraph` 로 묶고 제목에 이름 · 사양을 적는다 (`app-01 · 4 vCPU · 16GB · SSD 200GB`).
- 모양: 서비스 `[ ]`, 미들웨어 `[[ ]]`, 저장소 `[( )]`, 사용자 `([ ])`. 라벨 두 번째 줄은 `<br/><i>역할</i>`.
- DB 는 어느 서비스가 **어느 스키마**를 읽고 쓰는지 선 라벨에 적는다 (`"읽기 · 쓰기 (스키마 web)"`). 다른 서비스 스키마를 직접 읽으면 그 선을 따로 표시한다.
- 선: 동기 호출은 실선 `-->`, 비동기(메시지 · 이벤트)는 점선 `-.->`. 라벨은 방식(REST · gRPC · MQ 큐 이름 · JDBC)을 짧게.
- 그림의 이름은 아래 구성 요소 표 · 서버 표의 이름과 같게 쓴다. 그림에 없는 설명(버전 · 이유)은 표에 둔다.

## 4. 표

양식대로 단계마다 「구성 요소 표」(종류 · 버전 · 역할 · 연결 · 서버)와 「서버 표」(용도 · CPU · 메모리 · 디스크 · OS · 위치 · 근거)를 둔다. 2차부터는 달라지는 행만 적는다.

## 5. 마무리

1. `aidure docs build` 로 그림을 확인한다. mermaid 문법이 틀리면 ✖ 로 알리고 사이트에는 원문과 오류 문구가 보인다.
2. 머리말 표는 짧게 둔다. 바뀐 이유는 결정 기록(`DEC-…`)에 두고 ID 를 건다. 이력은 git 이 남긴다 (그 프로젝트가 이력 표를 쓰고 있으면 그것을 따른다).
3. 구성이 바뀌는 결정이 나면 결정 문서에 남기고 이 문서의 해당 단계를 고친다.
