# idea: 아이디어 · 전체 그림

신규 구축은 문서부터 쓰지 않는다. **사용자가 무엇을 만들고 싶은지부터 대화로 끌어내고**, 합의한 것만 문서로 남긴다.

## 0. 시작

이 단계의 진행 방식은 정해져 있다 (다른 단계처럼 진행 방식을 따로 제안하지 않는다). 첫 답변에 한 줄로 알리고 바로 1번 질문을 한다:
「대화(8가지) → 전체 그림 → 범위(MVP 또는 전체) → 문서로 남기기. 이미 기획서가 있으면 건너뛸 수 있습니다.」

- **건너뛰기**: 사용자가 건너뛰자고 하거나 기획서가 이미 있으면 로드맵 `handoffs/PLAN.md` 의 이 단계 상태를 `✔ 건너뜀` 으로 둔다. 그래도 **3. 범위 정하기는 한다** (있는 기획서에서 기능 지도와 첫 범위를 뽑아 확인받는다. 다음 단계가 백로그를 쓴다). **규모(7번)도 묻는다**: 기획서에 수치가 없으면 묻고 `<기획 repo>/00-overview/scale.md` 에 남긴다.

## 1. 대화 (초안을 먼저 쓰지 않는다)

한 번에 하나씩 묻고, 답을 한두 줄로 되짚어 확인한 뒤 다음으로 간다. 결정이 필요한 것은 선택지 질문으로(권장안 첫째).

| 순서 | 묻는 것 | 끝나는 조건 |
|---|---|---|
| 1 | 무엇을 만들고 싶은가 (한 문장) | 사용자가 "맞다" 고 한 한 문장 |
| 2 | 누가 쓰는가 · 그 사람의 문제는 무엇인가 | 사용자 유형 1~3개와 각자의 문제 |
| 3 | 지금은 어떻게 해결하고 있나 (대안 · 경쟁 서비스) | 대안과 그 불편 |
| 4 | 핵심 흐름: 사용자가 처음부터 끝까지 하는 일 | 흐름 한 줄 (→ 로 이은 5~8단계) |
| 5 | 하지 않을 것 | 범위 밖 목록 |
| 6 | 제약: 일정 · 예산 · 플랫폼(웹 · 앱) · 꼭 써야 하는 기술 · 외부 연동 | 제약 표 |
| 7 | 규모: 사용자 수 · 동시 접속 · 하루 생기는 데이터 건수 · 증가량 · 보존 기간 · 피크 (지금 · 1년 · 3년) | 규모 표. 모르면 `미정` 과 미결. 구조를 「작게」 정하는 근거가 된다 |
| 8 | 성공 기준: 무엇이 되면 성공인가 | 확인 가능한 기준 1~3개 |

- 사용자가 모르는 것은 지어내지 않고 미결로 둔다. 업계 관례로 제안할 수 있는 것은 근거와 함께 권장안으로 낸다.
- 답이 길어지면 표로 정리해 보여 주고 확인받는다.

## 2. 전체 그림

대화가 끝나면 한 번에 보여 주고 고칠 곳을 묻는다.

- **핵심 흐름 그림** (mermaid · 대화에서는 그림 규칙대로)
- **기능 지도**: 영역 × 기능 표 (영역 = 사용자 · 관리 · 외부 연동 등). 기능마다 한 줄
- **시스템 구성 개략**: 화면 · 서버 · DB · 외부 서비스 (구성 요소만. 구성도 · 서버 사양은 다음 단계에서 `architecture` 스킬)
- **결정**: 대화 중 정한 것 (결정마다 한 줄, 대안이 있었으면 고른 이유)

## 3. 범위 정하기 (진행 방식대로)

| 진행 방식 (`workspace.json` project.approach) | 정하는 것 |
|---|---|
| MVP · 스프린트 (`sprint`) | 기능 지도에서 **끝까지 동작하는 최소 기능(MVP)** 하나 (많아야 몇 개). 줄이는 것은 기능 수이고, 그 기능의 완성도(오류 처리 · 사이드이펙트 · 테스트)는 줄이지 않는다. 나머지는 로드맵 `## 백로그` 에 기능 이름 한 줄씩. 첫 스프린트의 목표 · 기능은 다음 단계 「스프린트 계획」 에서 정한다 |
| 워터폴 · 전체 (`full`) | 기능 지도 전체를 이번 범위로. 단계별(요구사항 → 설계 → 구현 → 테스트) 일정을 묻는다 |

진행 방식을 바꾸려면 `aidure approach sprint|full`. 로드맵에 아직 아무것도 적지 않았으면 새 진행 방식의 뼈대로 다시 만들어지고, 백로그 · 날짜 · 끝낸 단계가 있으면 그대로 남는다 (그때는 단계 표만 진행 방식에 맞게 고치고 백로그 · 기록은 지우지 않는다).

## 4. 남기는 것 (사용자가 확인한 뒤)

같은 사실을 두 곳에 쓰지 않는다. 기획 repo 뼈대 기준 위치다.

| 산출물 | 정본 위치 |
|---|---|
| 한 문장 · 범위(포함 · 제외 = 하지 않을 것) · 핵심 흐름 | `<기획 repo>/00-overview/overview.md` |
| 사용자 · 문제 · 지금의 대안 · 성공 기준 · 기능 지도(첫 범위 열 = MVP 의 정본) · 제약 | `<기획 repo>/00-overview/idea.md` |
| 규모 (사용자 · 데이터량 · 증가 · 보존 · 응답 목표) | `<기획 repo>/00-overview/scale.md` (옛 뼈대면 `packs/core/assets/scale/template.md` 를 복사) |
| 요구 목록 초안 (기능 지도의 기능 한 줄 = 요구 한 줄) | `<기획 repo>/20-features/requirements.md` |
| 시스템 구성 개략 (구성 요소만) | `<기획 repo>/10-system/architecture.md` 의 1차 구성 (자리표시를 바꾼다) |
| 결정 | `<기획 repo>/90-decisions/` (결정마다 한 파일) |
| 백로그(나중 기능 이름) · 워터폴이면 단계별 일정(시작 · 완료 칸) | 워크스페이스 `handoffs/PLAN.md` |

- 기획 repo 가 없거나 폴더가 다르면 그 repo 의 기존 구조를 따르고, 없으면 사용자에게 위치를 묻는다.
- 끝나면 로드맵의 이 단계를 `✔` 로 바꾸고 다음 단계(MVP 면 「스프린트 계획」, 워터폴이면 「계획」)를 추천한다. 그때 로드맵을 프로젝트에 맞게 고칠지도 묻는다.
