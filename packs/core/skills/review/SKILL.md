# review — 변경사항 코드 리뷰

## 1. 변경 모으기

- 변경이 어느 repo 에 있는지부터 본다: `node packs/core/bin/repo-activity.js` 의 미커밋·미푸시 수.
- repo 마다 `git -C <repo> status` · `git -C <repo> diff` (스테이징 포함이면 `diff HEAD`). 사용자가 브랜치·커밋 범위를 주면 그 범위로.

## 2. 점검 항목

| 항목 | 보는 것 |
|---|---|
| 정확성 | 로직 오류, 경계값, NULL/빈 값, 동시성, 트랜잭션 경계 |
| 에러 처리 | 삼킨 예외, 사용자에게 500 이 새는 입력, 로그만 찍고 계속하는 경로 |
| 계약 동기화 | API·스키마·응답 필드를 바꿨다면 호출부·생성 클라이언트·문서·데이터가 함께 바뀌었는가 (`.agents/rules/core--30-change-impact.md` ②③) |
| 반쪽 적용 | 읽기만 바꾸고 쓰기(생성·복사·삭제)를 빠뜨리지 않았는가 |
| 보안 | 인젝션(SQL·명령·경로), XSS, 권한 검사 누락, 비밀값 하드코딩 |
| 하드코딩 | 환경·계정·호스트·매직 넘버 — 설정이나 상수로 |
| 불필요한 것 | 죽은 코드, 디버그 출력, 장황하거나 낡은 주석 |
| 검증 | 테스트·검증표가 바뀐 경로를 모두 덮는가 (diff 에서만 뽑은 케이스가 아닌가) |
| 프로젝트 룰 | `AGENTS.md` 와 해당 on-demand 룰의 컨벤션 |

## 3. 보고

- 결론 먼저: "블로커 N · 권장 M · 사소 K".
- 발견마다 `파일:라인` · 무엇이 문제인지 · 수정안. 확인 못 한 추정은 "추정" 이라고 적는다.
- 문제가 없으면 그렇게 말하고 커밋 메시지를 제안한다 (커밋은 사용자가 요청할 때만).
- 리뷰만 한다 — 사용자가 요청하기 전에는 고치지 않는다.
