# ticket: 이슈·티켓 한 건 처리

입력: 티켓 번호와 내용(현상·재현 조건·발생 시각). 없으면 먼저 묻는다.

## 1. 영향 범위
- 현상이 나타나는 화면·API·배치와, 같은 데이터를 쓰는 다른 경로를 찾는다 (`.agents/rules/core--30-change-impact.md` 의 전수 검색).
- 운영 중인 시스템이면 운영 영향(몇 명·몇 건)을 조회로 확인한다. 운영 환경은 **조회만**.

## 2. 재현
- 개발·테스트 환경에서 같은 조건으로 재현한다. 재현 절차와 결과를 기록한다.
- **재현하지 못하면 여기서 멈추고 보고한다.** 추측으로 고치지 않는다.

## 3. 원인 확정
- 원인 코드를 `파일:라인` 으로 짚고, 왜 그 조건에서만 나는지 설명한다. 확인되지 않은 부분은 "추정" 으로 적는다.

## 4. 수정
- 티켓을 해결하는 최소 변경만. 발견한 다른 문제는 고치지 않고 "별도 티켓 후보" 목록에 적는다.
- 데이터 보정이 필요하면 SQL 스크립트를 만들고 dry-run 건수를 붙인다. 운영 실행은 승인받은 담당자가 한다.

## 5. 검증
- 재현 절차로 해결을 확인하고, 1 에서 찾은 다른 경로가 깨지지 않았는지 확인한다.
- 결과는 표로: 대상 / 케이스 / 방법 / 기대 / 실제 / 판정. 못 한 검증은 "미검증" 으로 적는다.

## 6. 조치 보고
```
[티켓 번호] 제목
- 현상:
- 원인:
- 조치: (변경 파일·커밋)
- 영향 범위:
- 재발 방지:
- 별도 티켓 후보: (있으면)
```
커밋·push·MR 은 사용자가 요청할 때만 한다.
