# 화면 테스트·검증 상세

요약 규칙은 `packs/frontend/rules/95-testing-and-verification.md`. 출처는 `packs/frontend/docs/SOURCES.md` (Testing Library · Playwright · 공개 AGENTS.md).

## 1. 층위 — 무엇을 어디서 확인하나

| 층위 | 확인하는 것 | 도구 예 | 쓰지 않는 곳 |
|---|---|---|---|
| 정적 | 타입·린트·포맷·접근성 린트 | `tsc`·ESLint·Prettier·프레임워크 a11y 린트 | — |
| 단위 | 순수 함수(포맷터·URL 파서·계산) | Vitest·Jest | 화면 흐름 |
| 컴포넌트 | 한 컴포넌트의 상태별 렌더·상호작용(로딩·빈·오류·권한 없음) | Testing Library + 테스트 러너, Storybook 상호작용 테스트 | 실제 서버 연동 |
| E2E | 사용자 흐름 전체(로그인→목록→저장), 라우팅·URL 상태 | Playwright·Cypress | 세부 분기 전수 |
| 시각 회귀 | 의도치 않은 모양 변화 | Playwright `toHaveScreenshot`, Storybook 시각 테스트 | 동작 검증 대체 |
| 접근성 자동 | 규칙 위반 일부 | axe 통합 | 키보드·낭독 확인 대체 |

- **프로젝트에 이미 있는 테스트 방식·위치·명명을 따른다.** 새 도구를 들이는 것은 묻는다.
- 바꾼 코드에 해당하는 테스트를 추가·갱신한다. 기존 테스트를 통과시키려고 **단언을 약하게 만들거나 테스트를 지우지 않는다** — 테스트가 틀렸다고 판단하면 이유를 적고 묻는다.

## 2. 테스트 작성 원칙

- 테스트가 소프트웨어가 쓰이는 방식과 닮을수록 믿을 수 있다(Testing Library) — **구현 세부(내부 state·함수 이름·CSS 클래스)가 아니라 사용자가 보는 결과**를 확인한다.
- 요소는 **역할·이름으로** 찾는다 — `getByRole('button', { name: 'Save' })` → `getByLabelText` → `getByText` … 마지막이 `data-testid`. 역할로 못 찾으면 그 자체가 접근성 결함일 수 있다.
- `data-testid` 를 쓰면 프로젝트 규칙(값 하나·명명)을 따른다.
- 기다림은 **자동 재시도 단언**(`findBy*`·`toBeVisible()` 등)으로. 고정 시간 대기(`sleep`·`waitForTimeout`)를 넣지 않는다 — 느린 CI 에서 깨지고 빠른 PC 에서 시간을 버린다.
- 테스트는 서로 독립 — 자기 데이터·쿠키·저장소. 앞 테스트가 만든 상태에 기대지 않는다.
- 우리가 통제하지 않는 외부 서비스는 네트워크 모킹. 서버 계약은 생성된 타입·목(mock) 핸들러로 맞춘다.
- 시각 회귀는 OS·브라우저마다 기준 이미지가 다르다 — 시각·난수·애니메이션 같은 변하는 부분은 가리고, 기준 이미지 갱신은 의도한 변경일 때만.

## 3. 상태별로 확인할 것 (컴포넌트·화면 공통)

| 상태 | 확인 |
|---|---|
| 로딩(첫 조회) | 스켈레톤, 레이아웃 흔들림 없음 |
| 재조회 | 직전 내용 유지 + 오버레이 |
| 빈 결과 | 빈 상태 문구·다음 행동 |
| 조회 실패 | 그 자리 오류 표시(빈 상태와 구분) |
| 저장 실패(4xx 필드 오류) | 필드 인라인, 입력 보존, 포커스 |
| 저장 실패(5xx·네트워크) | 배너 + 조회용 코드, 재시도 가능 |
| 성공 | 토스트, 보조기기 알림 |
| 권한 없음 | 비활성 + 이유 |
| 긴 값·많은 행 | 줄바꿈·말줄임, 페이지네이션 |
| 입력 경계 | 입력 · 미입력 · 초과(서버가 400 으로 막는가) |

## 4. 실제 브라우저 확인 (UI 를 바꿨을 때)

타입 검사·단위 테스트는 **기능이 맞는지**를 보지 **화면이 맞는지**를 보지 않는다. UI 를 바꿨으면 개발 서버를 띄워 브라우저에서 본다.

1. 바꾼 화면을 열고 주 흐름을 한 번 끝까지(생성·수정·삭제가 있으면 모두).
2. **응답이 끝난 뒤** 확인한다 — 로딩 중에 캡처하고 "0건" 으로 판정하지 않는다.
3. 콘솔 오류·경고 0, 네트워크에 실패한 요청이 없는지.
4. 키보드만으로 같은 흐름(Tab·Enter·Space·Esc), 포커스가 보이고 가려지지 않는지.
5. 좁은 폭(320px 또는 앱 최소 폭)과 200% 확대, 다크 모드가 있으면 양쪽.
6. 실제 데이터 모양 몇 가지 — 0건·1건·많은 건, 긴 문자열, 권한이 다른 계정.
7. 브라우저 자동화 도구가 있으면 그 결과(스크린샷·로그)를 남긴다. 확인하지 못했으면 "미검증" 으로 적는다.

## 5. 완료 전 명령

프로젝트가 정한 명령을 쓴다(패키지 스크립트·`Makefile`·README). 흔한 모양:

```bash
<pm> run lint        # 린트 (a11y 포함)
<pm> run typecheck   # 또는 tsc --noEmit
<pm> run test        # 단위·컴포넌트
<pm> run build       # 프로덕션 빌드 — 개발 서버에서만 안 보이는 오류(트리 셰이킹·환경 변수)를 잡는다
```

- 고친 범위의 테스트를 먼저 돌리고, 끝나기 전 전체를 한 번.
- 실패를 남긴 채 완료라고 하지 않는다. 기존부터 실패하던 것이면 그 사실을 적는다.
- 생성물(API 클라이언트·번역 추출물)을 바꿨으면 재생성 명령으로 만든 것인지 확인한다.
