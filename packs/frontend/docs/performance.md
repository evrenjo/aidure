# 화면 성능 상세 (Core Web Vitals · 예산 · 캐시 · 측정)

요약 규칙은 `packs/frontend/rules/85-performance.md`. 출처는 `packs/frontend/docs/SOURCES.md` (web.dev · Google Search Central · NN/g).

## 1. 무엇을 재나

| 지표 | 좋음 | 개선 필요 | 주로 망가뜨리는 것 |
|---|---|---|---|
| LCP | ≤ 2.5s | > 4s 나쁨 | 늦게 발견되는 주 이미지, 지연 로딩된 첫 화면 이미지, 렌더 차단 스크립트·CSS, 느린 API |
| INP | ≤ 200ms | > 500ms 나쁨 | 클릭 핸들러의 긴 동기 작업, 거대한 DOM, 입력마다 전체 재렌더 |
| CLS | ≤ 0.1 | > 0.25 나쁨 | 크기 없는 미디어, 늦게 끼우는 배너, 폰트 교체, 스켈레톤·실내용 높이 차 |

- 판정은 실제 방문의 **75번째 백분위**(모바일·데스크톱 따로). 개발 PC 한 번의 측정은 참고값이다.
- 로그인 뒤 업무 앱(첫 방문보다 오래 쓰는 화면)은 INP·CLS 가 체감에 더 크다. 공개 랜딩 페이지는 LCP 가 먼저다.
- "좋음" 경계 밖 수치(4s·500ms·0.25)는 web.dev 의 나쁨 기준이다.

## 2. 측정 절차 — 고치기 전과 후에 같은 방법으로

1. **재현 조건을 고정한다** — 같은 데이터 규모·같은 화면·브라우저 개발자 도구의 CPU/네트워크 제한(모바일 가정이면).
2. **어디가 느린지 본다** — 성능 패널(긴 작업·레이아웃·스타일 재계산), 네트워크 패널(워터폴·크기·캐시 여부), Lighthouse(실험실 점수와 진단), 실사용 지표가 있으면 RUM.
3. **원인이 서버면 화면에서 가리지 않는다** — 응답이 느린 API 는 그 엔드포인트와 수치를 보고한다.
4. **고친 뒤 같은 조건으로 다시 잰다.** 수치가 안 바뀐 최적화는 되돌린다(복잡도만 늘었다).

> 추정으로 최적화하지 않는다. 메모이제이션·캐시·가상화는 측정된 병목에만 쓴다.

## 3. 레이아웃 흔들림 (CLS)

- `<img>`·`<video>`·`<iframe>` 에 `width`/`height` 속성 또는 CSS `aspect-ratio`.
- 늦게 오는 영역은 `min-height` 로 자리를 확보하거나, 사용자 동작 뒤에만 끼운다. 사용자가 누른 뒤 500ms 안의 이동은 CLS 에서 빠진다(예상된 변화).
- 스켈레톤은 실제 행·카드와 같은 높이. 재조회 때는 직전 내용을 유지한다(`loading-state.md`).
- 애니메이션은 `transform`·`opacity`. `top`/`left`/`width`/`height`/`box-shadow` 애니메이션은 레이아웃·페인트를 다시 한다.
- 웹폰트는 대체 글꼴의 크기 보정(`size-adjust` 등)이나 `font-display` 전략, 핵심 폰트만 미리 로드.
- 뒤로·앞으로 이동이 bfcache 에 들어가게 — `unload` 핸들러를 쓰지 않는다.

## 4. 로드 (LCP) · 번들

- 첫 화면 밖 이미지·iframe 은 `loading="lazy"`. **첫 화면 주 이미지는 지연 로딩하지 않는다**(필요하면 `fetchpriority="high"`).
- 반응형 이미지: `srcset` + `sizes` 로 화면에 맞는 크기, 현대 형식(WebP·AVIF). 원본을 CSS 로 줄여 보이지 않는다.
- 라우트 단위 코드 분할, 무거운 위젯(차트·에디터·PDF 뷰어·지도)은 쓸 때 동적 import.
- **새 라이브러리의 비용**을 본다 — 번들 분석 도구로 크기를 확인하고, 한 함수 때문에 큰 라이브러리를 들이지 않는다. 날짜·숫자 포맷은 `Intl`, URL 은 `URL`/`URLSearchParams`, 깊은 복사는 `structuredClone` 처럼 플랫폼 API 가 먼저다.
- 트리 셰이킹이 되게 필요한 것만 import(`import { x } from`), 전체 네임스페이스 import 로 큰 라이브러리를 통째로 끌어오지 않는다.
- 렌더를 막는 스크립트를 `<head>` 에 동기로 넣지 않는다(`defer`·`type="module"`).

## 5. 반응 (INP)

- 이벤트 핸들러는 **화면에 보일 최소한만 동기로** — 누른 표시·선택 상태를 먼저 그리고, 저장·로그·계산은 뒤로 미룬다(작업을 나누고 메인 스레드에 양보).
- 한 작업 안에서 스타일을 쓰고 곧바로 레이아웃 값을 읽는 것을 반복하지 않는다(강제 동기 레이아웃).
- DOM 크기가 렌더 비용이다 — 수백 행 이상은 페이지네이션·가상 스크롤, 화면 밖 긴 섹션은 `content-visibility: auto` 검토.
- 타이핑마다 도는 요청은 디바운스 + 이전 요청 취소(`AbortController`). 늦게 도착한 옛 응답이 새 결과를 덮지 않게.
- 무거운 계산(대용량 파싱·집계)은 Web Worker 로 옮길 수 있는지 본다.

## 6. 데이터 요청

- 같은 데이터를 여러 컴포넌트가 각자 부르지 않는다 — 서버 상태 캐시 라이브러리(키 기반 중복 제거·재검증)에 맡긴다.
- 폭포수 요청(A 끝나고 B, B 끝나고 C)을 만들지 않는다 — 서로 독립이면 병렬로, 서버가 한 번에 줄 수 있으면 API 를 제안한다.
- 목록은 서버 페이지네이션. 전량을 받아 화면에서 자르지 않는다.
- 폴링은 화면이 보일 때만, 탭이 숨으면 멈춘다.

## 7. HTTP 캐시 (빌드 산출물)

| 자원 | 헤더 |
|---|---|
| 해시가 붙은 정적 파일(`app.3f9a1c.js`) | `Cache-Control: max-age=31536000, immutable` |
| HTML · 해시 없는 파일 | `Cache-Control: no-cache` + `ETag`/`Last-Modified` (매번 재검증) |
| 민감한 응답 | `no-store` |

- 헤더는 서버·CDN 설정이다. 화면 쪽 책임은 **빌드가 파일명에 해시를 붙이게 두는 것**과, 배포 뒤 옛 청크를 못 찾는 경우(동적 import 실패)를 처리하는 것 — 새로고침 안내 등 프로젝트 방식대로.
- 서비스 워커를 새로 들이는 것은 캐시 수명 전체를 바꾸는 결정이라 묻는다.

## 8. 성능 예산

- 예산 종류: **양**(번들·이미지·폰트 크기·요청 수) · **시점**(LCP·INP 등) · **규칙 점수**(Lighthouse).
- 프로젝트에 예산이 있으면 CI(번들 크기 검사·Lighthouse CI)가 지킨다. 넘으면 최적화하거나, 기능을 빼거나, 추가를 막는다 — 예산을 조용히 올리지 않는다.
- 없으면 새로 만드는 것은 제안으로. 변경 전후 번들 크기 차이는 리뷰 설명에 적을 만하다.

## 9. 공개 페이지 (검색 노출이 필요한 화면)

로그인 뒤 업무 화면에는 해당이 없다. 검색에 노출돼야 하는 페이지만.

- 페이지마다 고유한 `<title>` 과 `meta description`.
- 이동은 `<a href>` 진짜 링크 — 검색 엔진은 `href` 가 있는 `<a>` 만 링크로 따라간다. 라우팅은 History API(해시 `#/` 라우팅 지양).
- 없는 페이지는 404 상태(또는 `noindex`) — 클라이언트 렌더 화면이 200 으로 "없음" 을 그리면 soft 404 가 된다.
- 중요 콘텐츠는 초기 HTML(서버 렌더·정적 생성)에 있거나 렌더 후 보이게. 구조화 데이터(JSON-LD)는 프로젝트 필요 시.
- 색인되면 안 되는 화면(관리자·미리보기)은 `noindex`.
