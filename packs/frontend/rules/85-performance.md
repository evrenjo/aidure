## 목표 — Core Web Vitals (방문의 75번째 백분위, 모바일·데스크톱 따로)

| 지표 | 좋음 | 뜻 |
|---|---|---|
| LCP (Largest Contentful Paint) | ≤ 2.5s | 주 콘텐츠가 보이기까지 |
| INP (Interaction to Next Paint) | ≤ 200ms | 클릭·입력 뒤 다음 화면 갱신까지 |
| CLS (Cumulative Layout Shift) | ≤ 0.1 | 보던 내용이 밀리는 정도 |

로그인 뒤 업무 화면처럼 첫 로드보다 상호작용이 중요한 앱은 INP·CLS 가 먼저다. 프로젝트에 성능 예산이 있으면 그것을 따른다.

## 레이아웃이 밀리지 않게 (CLS)

- 이미지·영상·iframe 에 `width`·`height` 또는 `aspect-ratio` 로 자리를 잡는다.
- 늦게 오는 내용(배너·알림·광고·비동기 섹션)은 자리를 미리 잡거나(`min-height`) 사용자 동작 뒤에만 끼운다. 보던 내용 **위에** 끼워 넣지 않는다.
- 로딩 자리표시(스켈레톤)는 실제 내용과 같은 크기로. 재조회 때 내용을 비우지 않는다(frontend 피드백 룰).
- 애니메이션은 `transform`·`opacity` 로. `top`·`left`·`width`·`height` 애니메이션은 레이아웃을 다시 계산한다.
- 웹폰트는 대체 글꼴 크기를 맞추거나 `font-display` 를 정해 글자가 바뀔 때 밀리지 않게.

## 덜 받고 늦게 받기 (LCP)

- 첫 화면 밖의 이미지는 `loading="lazy"`. **첫 화면의 주 이미지(LCP 후보)는 지연 로딩하지 않는다.**
- 무거운 화면·차트·에디터·거의 안 여는 다이얼로그는 라우트·동적 import 로 나눠 필요할 때 받는다.
- 새 라이브러리는 번들 크기를 보고 들인다 — 한 함수 때문에 큰 라이브러리를 통째로 넣지 않는다. 이미 있는 유틸·플랫폼 API(`Intl`·`URL`·`fetch` 등)로 되면 그것을 쓴다.

## 반응을 막지 않기 (INP)

- 클릭·입력 핸들러에서 무거운 계산을 동기로 하지 않는다 — 먼저 화면을 갱신하고(누른 표시), 무거운 일은 나누거나 뒤로 미룬다.
- 수백 행이 넘는 목록은 페이지네이션이나 가상 스크롤. 타이핑마다 도는 검색·미리보기 요청은 디바운스하고 이전 요청을 취소한다.
- 같은 데이터를 화면 여러 곳에서 각자 부르지 않는다 — 공용 캐시(서버 상태 라이브러리)에 맡긴다.

## 예산·캐시

- 프로젝트에 성능 예산(번들 크기·Lighthouse 점수 CI)이 있으면 넘기지 않는다 — 넘으면 줄이거나 빼거나 묻는다. 예산을 조용히 올리지 않는다.
- 빌드 산출물 파일명의 해시(긴 캐시의 전제)를 끄지 않는다. 배포 뒤 옛 청크를 못 찾는 동적 import 실패는 프로젝트 방식대로 처리한다. 서비스 워커를 새로 들이는 것은 묻는다.

## 공개 페이지 (검색 노출이 필요한 화면만)

- 페이지마다 고유한 `<title>`·설명, 이동은 `href` 가 있는 진짜 `<a>`, 라우팅은 History API.
- 없는 페이지는 404 상태나 `noindex` — 200 으로 "없음" 을 그리면 soft 404 가 된다. 색인되면 안 되는 화면은 `noindex`.

## 측정 먼저

- **느리다는 추정으로 최적화하지 않는다.** 브라우저 성능 패널·Lighthouse·실사용 지표(RUM)로 어디가 느린지 먼저 잰다. 고친 뒤 같은 방법으로 다시 잰다.
- 메모이제이션·캐싱 같은 미세 최적화는 측정된 병목에만. 스택 팩이 금하는 기본 수단이면 따른다.
- 느린 원인이 서버 응답이면 화면에서 가리지 말고 그 API 를 보고한다.
