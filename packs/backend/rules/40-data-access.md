## 기본

- **파라미터 바인딩만** — 입력값을 SQL 문자열에 이어 붙이지 않는다(ORM 의 원시 쿼리·동적 조건 조립 포함). 정렬 컬럼·방향처럼 바인딩이 안 되는 자리는 **허용 목록**에서 고른다.
- **N+1 을 의식한다** — 목록 한 번 + 행마다 조회는 반복문 밖 한 번의 조인·IN 조회로. 지연 로딩이 있는 ORM 이면 목록 경로에서 몇 번 쿼리가 나가는지 확인한다.
- **필요한 컬럼·행만** — 목록 조회에 전체 모델을 통째로 올리지 않는다. 페이지 없는 전체 조회는 건수 상한을 안다.
- **인덱스를 확인한다** — 새 조회 조건·정렬·조인 키, 특히 **여러 컬럼을 함께 거는 조건**(외래 키 + 기간, 커서 페이지)은 그 조합을 덮는 인덱스가 있는지 본다. 한 컬럼 인덱스는 복합 조건을 덮지 못한다. 인덱스 추가는 스키마 변경이다(db 팩 규칙).
- **최소 권한** — 앱 DB 계정에 스키마 변경·다른 스키마 권한을 새로 요구하는 코드를 만들지 않는다. 필요하면 사람에게.
- 조회 기준(테이블·조인 키·조건)을 바꾸면 **같은 데이터를 쓰는 쓰기 경로**가 새 기준을 채우는지 전수로 확인한다 (core 의 변경 영향 점검).

## 수단 고르기

1. ORM·쿼리 빌더의 기본 기능으로 되는가
2. 타입 안전한 동적 쿼리 도구로 되는가 (조인·동적 조건·집계 포함)
3. 둘 다 안 되면 원시 SQL + **왜 원시인지 주석 1줄**

- 원시 SQL 이 정당한 경우는 좁다: 추상화에 없는 구문(`INSERT … SELECT` 등), DB 카탈로그 조회, 다른 스키마·DB 참조, 시퀀스, 아래 대량 처리 예외.
- **전염 주의** — 원시 SQL 이 이미 있는 파일이라는 것은 사유가 아니다. 새 함수마다 위 순서를 다시 밟는다.

## 동시 수정·일관성

- **읽고-판단하고-쓰는** 코드(재고 차감·상태 전이·채번·"없으면 만든다")는 동시 요청 두 개가 같은 값을 읽는 경우를 가정한다. 막는 수단은 셋 중 기존 관례에 있는 것:
  1. **유니크 제약** — "없으면 만든다" 의 중복은 제약이 막고, 위반을 409 등 업무 오류로 바꾼다. 앱 코드의 존재 확인만으로는 막히지 않는다.
  2. **낙관적 잠금** — 버전 컬럼으로 갱신 충돌을 감지해 409 로. 사람이 화면에서 고치는 행에 알맞다.
  3. **비관적 잠금·조건부 UPDATE** — `UPDATE … SET qty = qty - 1 WHERE id = ? AND qty > 0` 처럼 판단을 한 문장에 넣거나, 짧은 트랜잭션에서만 행 잠금.
- 트랜잭션은 짧게 — 사용자 입력·외부 호출을 트랜잭션 안에서 기다리지 않는다. 격리 수준은 기본값을 바꾸지 않는다(필요하면 근거와 함께 사람에게).
- 여러 테이블을 바꾸는 한 동작은 한 트랜잭션에서. 일부만 커밋되는 경로가 없는지 본다. 도중에 실패하면 **전부 되돌리는 쪽**(fail closed)으로.
- 스키마를 바꾸는 코드와 함께 배포되는 변경은 **옛 코드·새 코드가 잠시 함께 도는 동안** 둘 다 동작해야 한다 — 컬럼 추가는 먼저, 삭제는 코드가 떠난 다음 배포에서. 스키마 변경 절차는 db 팩 규칙.

## 대량 처리

- 기본은 ORM 의 일괄 저장(배치 크기 설정으로 보강). 영속성 캐시·세션을 우회하는 일괄 UPDATE 는 같은 트랜잭션의 객체를 옛 값으로 남긴다.
- **실측 1만 행 이상**인 계층 복제·일괄 삭제·단일 컬럼 치환에 한해 집합 SQL(`INSERT … SELECT` / `UPDATE … WHERE` / `DELETE … WHERE`)을 쓴다. 조건 전부:
  1. 같은 트랜잭션에서 대상 객체를 메모리에 올리지 않는다 (불가피하면 실행 뒤 캐시를 비운다).
  2. 범위를 **파티션을 완전히 특정하는 키 전체**로 한정한다 — 상위 ID 하나로 걸지 않는다.
  3. 주석에 실측 건수와 예외 사유 1줄.
- 온라인 요청·주기 작업에서 사용자 데이터 테이블을 **상한 없이 한 번에** 지우거나 고치지 않는다 — 잠금이 트랜잭션 내내 잡혀 다른 쓰기를 막는다. 건수 단위로 나눠 커밋하고, 조건 컬럼에 인덱스가 있는지 본다.
- "언젠가 커질 수 있으니" 는 사유가 아니다. 실측 건수로 판단한다.
- 백필·정리 SQL 은 db 팩 「데이터 반영·백필·정리 SQL」을 따른다. 그 팩이 없으면 최소한 멱등(`NOT EXISTS` 가드)·롤백되는 시험 실행으로 건수 확인·파괴적 실행은 사람 승인.

## 값 고르기

- "최신·최대" 를 고를 때 문자열 사전순 비교를 그대로 쓰지 않는다 — 업무 순서가 있는 코드값은 **이미 정의된 순서 상수**가 있는지 먼저 찾는다.
- 같은 타입 인자가 줄줄이 이어지는 복합 키는 **이름 있는 값 객체**로 넘긴다 — 순서를 바꿔도 컴파일·실행이 통과해 조용히 다른 행을 읽는다.
- 시각은 저장·비교 기준 시간대를 기존 관례에서 확인한다(서버 로컬 시각을 암묵적으로 쓰지 않는다).
