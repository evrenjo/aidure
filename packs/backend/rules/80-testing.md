테스트 실행이 자동으로 허용되는지·어떤 명령으로 돌리는지는 project 팩 규칙과 저장소의 기존 설정을 따른다.

## 무엇을

- **바꾼 동작마다 테스트** — 추가·변경한 동작은 그 변경이 없으면 실패하는 테스트로 증명한다. 이미 있던 로직·라이브러리 동작을 새로 테스트하지 않는다.
- **버그 수정은 재현부터** — 먼저 실패하는 테스트를 쓰고, 고친 뒤 통과를 확인한다.
- 경계에서 막는 규칙(검증·인가)은 **거부 케이스**를 반드시 넣는다: 필수 누락, 길이·정밀도 초과, 다른 사용자의 ID, 권한 없는 역할.
- 동시성·멱등 처리를 넣었으면 같은 요청 두 번·동시 두 번을 테스트한다.
- 외부 호출을 넣었으면 타임아웃·오류 응답·재시도 소진 경로를 테스트한다(성공 경로만 두지 않는다).
- API 응답 형태를 바꿨으면 기존 소비자 기준의 계약(스냅샷·스키마·계약 테스트)이 있는지 보고 함께 갱신한다.

## 어떻게

- 층을 나눈다 — 업무 규칙은 빠른 단위 테스트로 많이, DB·직렬화·인가 설정은 통합 테스트로 필요한 만큼, 끝-끝 테스트는 핵심 흐름만. 아래 층이 이미 증명한 것을 위 층에서 반복하지 않는다.
- **구현이 아니라 관찰되는 동작**을 확인한다 — 내부 함수 호출 순서를 검사하는 테스트는 리팩터링마다 깨진다.
- 외부 HTTP 서비스는 테스트 대역(스텁 서버 등)으로 바꾸고, 우리 DB 는 실제 엔진으로.
- **실제에 가까운 DB** — 쿼리·제약·잠금 동작은 실제 DB 엔진(컨테이너 등)으로 검증한다. 다른 엔진·메모리 DB 로 통과한 것은 증거가 약하다. 저장소에 이미 있는 테스트 DB 방식을 쓴다.
- 시간·난수·외부 호출은 주입해서 고정한다. 현재 시각을 직접 읽는 코드는 테스트가 흔들린다.
- 로그 문자열을 그대로 대조하지 않는다 — 구조화 필드나 동작 결과로 확인한다.
- 테스트 데이터는 합성으로. 실제 고객 데이터·비밀값을 픽스처에 넣지 않는다.
- 테스트끼리 순서·공유 상태에 의존하지 않는다. 만든 데이터는 테스트가 치운다.

## 보고

- 돌린 테스트와 결과를 적는다. 못 돌렸으면 "미실행" 이라고 적고 이유를 쓴다 — 통과했다고 쓰지 않는다.
