# 백엔드 API 참고 — 오류 형식·상태 코드·멱등 키·페이지·값 표현·호환성

> 이 문서는 **참고용**이다. 프로젝트에 이미 응답·오류·페이지 관례가 있으면 그것을 따른다(「백엔드 API 계약·검증·오류 메시지」).
> 관례가 전혀 없는 신규 프로젝트에서 안을 제시할 때만 여기서 고른다. 출처는 `SOURCES.md`.

## 1. 오류 응답 — RFC 9457 Problem Details

미디어 타입 `application/problem+json`. 필드:

| 필드 | 뜻 |
|---|---|
| `type` | 오류 종류를 가리키는 URI (문서 링크 가능). 없으면 `about:blank` |
| `title` | 종류에 대한 짧은 사람용 요약 (같은 `type` 이면 같은 문장) |
| `status` | HTTP 상태 코드 (응답 코드와 같게) |
| `detail` | 이번 발생에 대한 설명 — 사용자에게 보여도 되는 문장만 |
| `instance` | 이번 발생을 가리키는 URI (선택) |

- 확장 필드를 더할 수 있다 — 예: 필드 오류 목록 `errors: [{ "field": "name", "message": "…" }]`, 추적 ID `traceId`.
- `detail` 에 스택트레이스·SQL·내부 ID 를 넣지 않는다. `detail` 은 사람용이라 클라이언트가 파싱하지 않는다 — 기계가 분기할 값은 확장 필드로.
- 클라이언트는 모르는 확장 필드를 무시해야 한다(그래서 필드를 더하는 것은 안전하다).
- 기계용 오류 코드를 두면 그 문자열은 API 계약이다 — 바꾸지 않고 문서화한다(Azure·Google AIP-193).

## 2. 상태 코드 — 자주 헷갈리는 것

| 상황 | 코드 |
|---|---|
| 형식·검증 실패 | 400 (프로젝트에 따라 422) |
| 인증 정보 없음·만료 | 401 |
| 인증됐지만 권한 없음 | 403 (존재 자체를 숨길 땐 404 — 관례대로) |
| 상태 충돌·중복 생성·낙관적 잠금 충돌 | 409 |
| 조건부 요청(`If-Match`) 불일치 | 412 |
| 한도 초과 | 429 + `Retry-After` |
| 비동기 수락 | 202 + 상태 조회 위치 |
| 생성 성공 | 201 (+ `Location`) |
| 본문 없는 성공 | 204 |
| 허용 안 된 메서드 | 405 + `Allow` 헤더 |
| 본문이 너무 큼 | 413 |
| 받지 않는 `Content-Type` | 415 |
| 줄 수 없는 `Accept` | 406 |
| 일시 불가(과부하·점검) | 503 (+ `Retry-After`) |
| 그 외 서버 결함 | 500 — 내부 내용 없이 |

- 안전한 메서드(RFC 9110 §9.2.1): GET·HEAD·OPTIONS·TRACE — 상태를 바꾸지 않는다.
- 멱등 메서드(§9.2.2): 안전한 메서드 + PUT·DELETE. 연결이 끊기면 클라이언트가 자동 재시도할 수 있다. POST·PATCH 는 멱등하지 않다.
- 가장 **구체적인** 코드를 쓰되, 흔한 코드 안에서 고른다(클라이언트가 모르는 코드는 오히려 해가 된다).

### 권한 없음 vs 없음 — 가이드마다 다르다

| 출처 | 입장 |
|---|---|
| Google AIP-193 | 권한부터 확인해 403, 권한이 있을 때만 404 |
| OWASP (IDOR·Authorization) | 존재 여부가 민감하면 권한 없는 사용자에게 404 로 숨길 수 있다 |

→ 킷 규칙: **기존 관례를 따르고, 새로 정하면 프로젝트 전체에 같게.**

## 3. 멱등 키 (`Idempotency-Key` 헤더, IETF 초안)

재시도될 수 있는 POST·PATCH 에 쓴다.

1. 클라이언트가 요청마다 유일한 키(UUID 등)를 헤더로 보낸다. 재시도에는 **같은 키**.
2. 서버는 (키, 호출 주체, 엔드포인트) 로 처리 기록을 저장한다. 본문 지문(해시)을 함께 저장한다.
3. 같은 키 재요청:
   - 처리 끝남 → **처음 결과를 그대로** 돌려준다(오류 결과 포함 여부는 정책으로 정한다).
   - 아직 처리 중 → 409.
   - 같은 키에 다른 본문 → 422.
4. 키가 필요한 엔드포인트에 키가 없으면 400.
5. 보존 기간(예: 24시간 이상)을 정하고 문서에 적는다.

처리 기록 저장과 본 처리가 한 트랜잭션에 있어야 "처리됐는데 기록이 없음" 이 생기지 않는다(AWS Builders' Library).
자연 키가 있는 생성(주문 번호 등)은 유니크 제약만으로도 같은 효과를 낼 수 있다(Zalando 의 "보조 키" 방식).

| 세부 | 출처별 선택 |
|---|---|
| 처음 요청이 5xx 였을 때 | Stripe: 결과(500 포함)를 저장해 그대로 돌려준다. 단 검증 실패·동시 충돌로 **실행이 시작되지 않은** 요청은 저장하지 않아 재시도 가능 |
| 키 형식 | Stripe: 최대 255자, UUIDv4 권장, 개인정보 금지. Google AIP-155: UUID |
| 보존 기간 | Stripe: 24시간 이상. IETF 초안: 정하고 문서화. Google: 합리적 기간 |
| 원래 자원이 지워진 뒤 늦게 온 재시도 | AWS: 처음과 의미상 같은 응답을 준다(기록은 자원보다 오래 둔다) |
| 헤더 이름 | IETF 초안·Stripe: `Idempotency-Key` / Azure: `Repeatability-Request-ID` / Google: 본문 `request_id` — **기존 관례** |

## 4. 페이지

| 방식 | 장점 | 주의 |
|---|---|---|
| 번호·오프셋 | 임의 페이지 이동, 총건수 표시 | 깊은 페이지가 느리다. 중간 삽입·삭제 시 중복·누락 |
| 커서(키셋) | 큰 데이터·자주 바뀌는 데이터에서 일정한 성능 | 임의 페이지 이동 없음. 커서는 **불투명**(클라이언트가 해석·조립하지 않음) |

- 공통: 페이지 크기 기본값·최댓값, 결정적 정렬(마지막에 유일 키), 다음 페이지 유무 표시.
- 크기 0·미지정 → 기본값, 최댓값 초과 → 최댓값으로 줄임(또는 400), 음수 → 400 (AIP-158).
- 커서는 URL 에 실어도 안전한 불투명 문자열, 끝이면 비우거나 생략. 커서가 인가를 대신하지 않는다.
- 총건수는 비싸다 — 필요할 때만 계산한다(Zalando·Azure 둘 다 기본 제공을 권하지 않는다).
- 페이지 사이에 데이터가 바뀌면 행이 건너뛰거나 겹칠 수 있음을 문서에 적는다(Azure).

## 5. 호환성 — 깨지는 변경 목록

| 변경 | 판정 |
|---|---|
| 응답에 선택 필드 추가 | 안전 (클라이언트는 모르는 필드를 무시해야 한다) |
| 요청에 선택 필드·파라미터 추가 | 안전 (기본값이 옛 동작과 같을 때) |
| 새 엔드포인트 | 안전 |
| 필드 삭제·이름 변경·타입 변경 | **깨짐** |
| 선택 → 필수 | **깨짐** |
| 기본값·의미·단위 변경 | **깨짐** (조용해서 더 위험) |
| 응답 열거값 추가 | 클라이언트가 모르는 값을 처리하지 못하면 깨짐 — 확장 가능 열거로 문서화했을 때만 안전 |
| 오류 형식·상태 코드 변경 | **깨짐** |

| 오류 코드·기계용 사유(reason) 문자열 변경 | **깨짐** — 클라이언트가 분기에 쓴다 (Azure·Google) |
| 요청 검증을 더 엄격하게 | **깨짐** — 어제 되던 요청이 실패한다 |
| 자원 이름·ID 형식 변경 | **깨짐** |

깨는 변경이 필요하면: 새 버전(경로·헤더 등 기존 버전 방식) 또는 새 필드를 먼저 더하고 옛 필드를 폐기 예고 → 유예 → 제거.
폐기 알림에는 `Deprecation`(RFC 9745)·`Sunset`(RFC 8594) 응답 헤더를 쓸 수 있다.

### 버전 방식 — 가이드마다 다르다

| 출처 | 방식 |
|---|---|
| Zalando | 버전을 되도록 피하고, 필요하면 미디어 타입 버전. URL 버전 금지 |
| Azure (Microsoft) | 모든 요청에 `api-version` 쿼리 파라미터(날짜). 경로에 버전 금지 |
| Google AIP | 경로에 주 버전(`v1`) |

→ 킷 규칙: **기존 방식을 따른다.** 셋 다 공통: 한 버전 안에서는 깨는 변경을 하지 않는다.

## 6. 값 표현

| 값 | 기본 (기존 관례가 없을 때) | 근거 |
|---|---|---|
| 시각 | RFC 3339, UTC `Z` (`2026-01-31T06:43:40.252Z`) | Zalando 169, RFC 3339 |
| 날짜만 | `YYYY-MM-DD` (시각·시간대 없음) | RFC 3339 full-date |
| 금액 | `{"amount": "99.95", "currency": "EUR"}` — 십진(문자열 또는 decimal), ISO 4217 | Zalando 173 |
| 국가·언어 | ISO 3166-1 alpha-2, ISO 639-1 / BCP 47 | Zalando 238 |
| 큰 정수 | ±(2^53−1) 을 넘을 수 있으면 문자열 | RFC 8259 §6 |
| 열거값 | 새 값이 추가될 수 있음을 문서에 적는다(확장 가능 열거). 클라이언트는 모르는 값을 견딘다 | Zalando 112, Azure |
| `null` | `null` 과 필드 생략을 같은 뜻으로. 불리언에 `null` 금지. 빈 배열은 `[]` | Zalando 122–124 |

- 서버 내부 저장·비교도 한 시간대 기준(대개 UTC)으로. 사용자 표시 시간대 변환은 표시 계층에서.
- 금액 계산은 십진 타입으로, 반올림 방식(HALF_UP·HALF_EVEN 등)을 한 곳에서 정한다. 합계 뒤 반올림인지 항목별 반올림인지 업무 규칙을 확인한다.

## 7. 캐시 헤더 (RFC 9111)

| 지시어 | 뜻 |
|---|---|
| `no-store` | 어떤 캐시도 저장하지 않는다 — 사용자별·민감 응답 |
| `no-cache` | 저장은 하되 매번 서버에 재검증 |
| `private` | 공유 캐시(프록시·CDN)는 저장하지 않는다 |
| `public` / `s-maxage` / `must-revalidate` | 인증된 요청의 응답을 공유 캐시가 재사용하려면 이 중 하나가 있어야 한다 |

- 조건부 요청: 응답에 `ETag` 를 주면 클라이언트가 `If-None-Match`(304) 로 아끼고 `If-Match`(412) 로 동시 수정을 막을 수 있다(Azure).

## 8. 요청 한도 응답

- 초과는 429 + `Retry-After`(RFC 6585·RFC 9110). 남은 한도를 알리는 `RateLimit`·`RateLimit-Policy` 헤더는 IETF 초안 단계 — 기존 관례가 있으면 그것을.

## 9. 오래 걸리는 작업 (Azure LRO 요약)

- 요청을 받으면 가능한 검증을 다 하고 202 + 상태 조회 위치(`Location`·`Operation-Location`) 를 돌려준다.
- 상태 자원은 `status`(대기·진행·성공·실패·취소)와 실패 시 오류 본문을 준다. 완료 뒤에도 일정 기간(예: 24시간) 조회 가능하게.
- 진행 중이면 `Retry-After` 로 조회 간격을 알린다.

## 10. 추적·요청 ID

- 요청마다 불투명한 요청 ID 를 만들고 응답 헤더·오류 본문·로그에 같은 값을 싣는다(Azure `x-ms-request-id` 형태, 이름은 관례대로).
- 클라이언트가 보낸 상관 ID·`traceparent` 는 받아서 이어 쓰되, 모르는 추적 헤더 때문에 요청을 실패시키지 않는다(Azure).
