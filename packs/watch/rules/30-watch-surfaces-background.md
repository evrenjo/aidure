## 전제 — 시스템이 예산을 정한다

워치의 백그라운드 실행 시간·갱신 횟수는 **시스템이 정하고 줄일 수도 있다**(배터리 부족, 운동·내비게이션 중 등). 요청한 시각에 깨어난다는 보장이 없다.
- 백그라운드 작업이 **한 번도 오지 않아도** 앱이 맞게 동작하게 한다 — 앱을 열 때 상태를 다시 맞춘다.
- 받은 백그라운드 작업은 빨리 끝내고 **완료를 알린다**. 완료하지 않은 작업은 예산을 계속 쓰고, watchOS 는 예산이 바닥나면 앱이 강제 종료된다.
- 기존 갱신 주기를 짧게 바꾸는 변경은 이유를 적고 묻는다.

## 컴플리케이션·타일·위젯

- **한눈에 보는 최신 정보** 한두 개. 넘치게 담지 말고 탭하면 앱의 해당 화면으로 가게 한다.
- **갱신은 드물게, 미리 계획해서** — 예측 가능한 값은 미래 시점 항목(타임라인)을 한 번에 만든다. 시간이 흐르며 바뀌는 글자(남은 시간·경과 시간)는 매분 갱신하지 말고 **시스템의 상대 시간 표시**를 쓴다.
- 플랫폼 한도를 넘지 않는다 — Wear OS 컴플리케이션 주기 갱신은 최소 300초(0 이면 푸시 갱신), 갱신 요청도 평균 5분 이상 간격. watchOS 위젯은 하루 갱신 예산이 있고 항목 간격은 약 5분 이상.
- 타일·컴플리케이션 코드 안에서 네트워크를 오래 기다리지 않는다 — 백그라운드 작업으로 받아 로컬에 저장하고, 앱·타일·컴플리케이션이 **같은 저장소**를 읽는다.
- 로그인이 필요한데 안 된 상태면 빈칸 대신 로그인하라는 안내를 보인다.
- 워치 화면 위라 남이 볼 수 있다 — 민감 정보는 넣지 않거나 가린다.

## 알림

- **중복을 막는다** — Wear OS 는 폰 알림을 워치로 기본 전달(브리징)한다. 워치 앱도 같은 알림을 만들면 둘 다 뜬다. 브리지 태그·해제 ID 로 조정하고, 매니페스트에서 전체 차단은 알림 유실 위험이 있어 쓰지 않는 게 기본.
- 첫 화면(짧게 보이는 단계)은 누가 보낸 무엇인지만 — 제목에 민감 정보를 넣지 않는다. 짧게 스쳐 가므로 중요한 정보를 거기에만 두지 않는다.
- 동작 버튼은 몇 개로, **가장 자주 쓰는 비파괴 동작을 맨 앞에**(watchOS 더블 탭이 첫 비파괴 동작을 실행).
- 전체 화면 알림에 기대지 않는다(Wear OS 는 지원하지 않는다). 커스텀 레이아웃보다 플랫폼 표준 스타일을 쓴다.

## 장시간 작업

- 1분 넘게 이어지는 작업(운동 기록·타이머·길게 녹음)은 플랫폼의 **진행 중 활동·백그라운드 세션** 방식으로 시작한다 — 워치 화면에서 한 번에 돌아올 수 있고 시스템이 앱을 유지한다. 짧은 일·홍보에는 쓰지 않는다.
- 세션 중에도 화면 갱신은 줄인다(초 이하 갱신 제거).

## 네트워크·배터리

- 동기화·정리처럼 무거운 일은 **충전 중으로 미룬다**. 급하지 않은 네트워크 요청도 마찬가지.
- 직접 wakelock 을 잡지 말고 시스템 작업 스케줄러를 쓴다. 센서는 원시 센서 대신 배치해 주는 플랫폼 건강 API 를 우선한다.
- 워치 쪽 응답은 작게 — 블루투스 경유 대역폭이 매우 좁을 수 있다. 폰용 필드·큰 이미지를 줄여 보낸다.
- 애니메이션은 짧은 전환 위주로.

## 확인

- 백그라운드·알림 동작은 **실기기에서** 본다. 개발 도구에서 실행 중이면 앱이 정상적으로 일시 중지되지 않아 결과가 다를 수 있다(watchOS 문서 명시) — 홈 화면에서 직접 실행해 로그로 확인한다.
- 배터리 영향은 플랫폼 도구(예: Wear OS 배터리 통계·Battery Historian)로 작업 횟수·wakelock 을 본다. 못 본 것은 미확인으로 보고한다.
